## What to fix

`lib.rust`'s shared dependency bundle is keyed on `(target, profile)` but the
builds that consume it enable extra `--features`. Every feature-gated crate is
therefore absent from the bundle and recompiles on each build — on the host and
in every guest, regardless of Nix store seeding.

`depsFor` (`lib/rust/default.nix:317`) takes exactly two arguments:

```nix
depsFor =
  {
    target ? null,
    profile ? defaultProfile,
  }:
  ...
  name =
    ...
    + (if target == null then "" else "-${target}")
    + profileSuffix profile;
```

Its consumers pass only those two — `buildTestArchive` (`:749`) and
`cargoChecks.clippy` (`:816`) both call `depsFor { inherit target profile; }` —
while the real build then enables consumer features (for one project:
`console,gym,probes` for the test archive, `--all-features` for clippy).

So the bundle contains the dependency closure for the *default* feature set
only. Anything an enabled feature pulls in — most visibly `bevy_egui`, plus
everything Cargo's feature unification drags along behind it — is missing, and
is compiled fresh every time. The name has no feature component, so two builds
with different features collide on one cache entry rather than getting one
each.

### How it presents

It does not look like a cache-key bug. It looks like broken artifact sharing:

- `sandbox status` reports `store db: host-seeded (host-built paths valid in
  the guest)` — correctly, since seeding is not the problem.
- The build logs show the bundle being decompressed and the vendor config wired
  correctly — also correctly.
- And then the guest compiles `bevy_render`, `bevy_pbr`, `bevy_egui`, `wgpu`
  and the rest anyway, for 15–25 minutes.

An operator watching that concludes the seeding is broken, or that the guest's
Nix is misconfigured. Two separate agents and one orchestrator reached exactly
that wrong conclusion over one session before someone read `depsFor`.

### Why it matters more than the wall-clock

A project's dispatch instructions steer agents to the Nix-backed menu commands
*because they are supposed to be cache hits*. When they are not, agents:

- burn 20+ minutes per verification, repeatedly;
- fall back to raw `cargo`, which is strictly slower still (it pays for the
  whole closure with no bundle at all);
- and end turns waiting on those builds, which is the failure mode card
  `01c94e` describes. A large share of the stalls that card documents were
  agents waiting on builds that should have been near-instant.

The three issues compound: builds that should be cached are not, the agent
cannot hold a long build in the foreground, and the nudge budget cannot span
it.

### Not fixable downstream

`katsuobushi.lib.rust` exports the high-level helpers only — not `depsFor` or
`craneLib` — so a consumer flake cannot patch its own bundle key. The fix has
to be here.

## Options

- **Key the bundle on features too.** Thread the consumer's feature list into
  `depsFor` and into the derivation name, so each feature set gets its own
  bundle. Correct, at the cost of one bundle per distinct feature set.
- **Build one bundle at the union of all consumers' features.** Fewer
  derivations, and a superset closure is still a cache hit for each consumer;
  costs more to build once and rebuilds all consumers when any feature moves.
- **Make the mismatch loud rather than silent.** Whatever the keying, a build
  that decompresses a bundle and then compiles a large fraction of the closure
  anyway could say so. The silence is what made this cost a session to find.

### Seam

- `depsFor` and its `name` construction — `lib/rust/default.nix:317-326`.
- Consumers passing only `{ inherit target profile; }` — `:749`
  (`buildTestArchive`), `:816` (`cargoChecks.clippy`); also `:765`, `:794` for
  the wasm targets.

## Acceptance criteria

- [ ] A build enabling non-default features reuses a bundle that contains those
      features' dependencies, rather than recompiling them
- [ ] Two builds with different feature sets do not collide on one bundle
- [ ] A consumer project's menu test command is a genuine cache hit on a second
      run in a fresh guest, verified by timing rather than by inspection
- [ ] If a bundle is still partially missed, the build says so rather than
      silently recompiling

**Also observed, could not reproduce:** the `opening lock file '….drv.lock': No
such file or directory` and `getting status of fd 18` failures reported from
guests. An agent ran `nix build .#tests-debug` and `.#tests-release`
back-to-back, re-ran both from cache, and ran `nix flake check` concurrently
with a fresh build to stress the daemon — all clean — and confirmed via
`/proc/<pid>/mountinfo` that `nix-daemon` holds a writable view of
`/nix/store`, ruling out a guest store-permission defect. Most likely a
transient race under concurrent VM provisioning, in the spirit of the 0.3.4
nix-db-snapshot livelock. Recorded here rather than as its own card, since it
could not be forced.
