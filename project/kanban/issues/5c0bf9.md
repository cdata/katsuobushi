## What's wrong

Guest `nix build` fails intermittently, in the build-sandbox setup, at a rate
that **tracks host/guest concurrency rather than elapsed time**. The failures are
transient — the same derivation succeeds on a later retry — but they cost a
dispatched agent its acceptance gate, which is the one thing it cannot route
around without weakening its own report.

Observed across ~25 instances in a single long orchestration run of a consumer
project (Bevy/Rust workspace, `vcpu = 8`, `mem = 12288`, `graphics.enable`).

## Four distinct error strings, all in build-sandbox setup

```text
error: getting status of fd 18/19: No such file or directory
error: Permission denied opening …drv.chroot
error: opening lock file '/nix/store/<hash>-tests-debug-0.1.0.lock': No such file or directory
error: cannot create "": File exists
```

They are not one typo'd path. They are the sandbox's *construction* failing in
several different ways.

**`ENOENT` on `open()` of a lock file is the most informative of the four.** An
unwritable directory yields `EROFS` or `EACCES`; `ENOENT` on a create means the
path is not where the client believes it is — which is what a stale dentry over a
network filesystem produces.

## The rate tracks concurrency

| stretch | concurrent VMs | fault rate |
| --- | --- | --- |
| early | 1–2, host mostly idle | ~2 of 10 instances |
| late | 3 + concurrent host builds | one reviewer hit it **4 times of 4** on the same derivation |

Same project, same flake, same day. The variable that changed is how many things
were touching the shared store at once.

**The host is affected too**, which is the point: one host-side
`nix develop -c tests all` failed with
`error extracting archive …/tests-release.tar.zst` and went green on a retry 45
seconds later. So this is not "guests are broken" — it is *concurrent nix
activity on one machine* being unreliable.

## Why the architecture makes this expected

`lib/sandbox/default.nix:843-852` shares the host's `/nix/store` into the guest
**read-only over 9p** as `/nix/.ro-store`, and `writableStoreOverlay` makes
`/nix/store` an overlayfs with that 9p share as **lowerdir** and `rw-store.img`
as upperdir.

So **anything the host writes into `/nix/store` — lock files, temp paths, build
outputs — lands in the very directory every guest is reading over 9p.** 9p
carries client-side dentry caching, so a guest can resolve a path (stale cache,
or a directory listing that still names it) and then fail to open it because the
host has since removed it. That is exactly the `ENOENT`-on-create signature, and
it is exactly the failure mode a `.lock` file's create-then-unlink lifecycle
would produce.

Verified end to end that the mount is live in both directions: a host-side
`git push` into `<state>/<instance>/sync.git` is visible to a **running** guest
immediately, and `findmnt` in the guest reports
`katsuobushi on /mnt/katsuobushi type 9p … trans=virtio`.

## What has been ruled out

- **Nix GC.** `nix-gc.timer` last ran three days before the run and was next due
  four days after. Nothing collected during it.
- **A broken guest store.** The doubled `/nix/store` mount and its read-only
  overlay are **normal** — a VM that built successfully all session shows the
  identical two mount entries and the identical `touch: Read-only file system`.
  That is ordinary NixOS (the daemon does the writing) and is *not* the fault. An
  orchestrator probe built around it produced false blocks on healthy VMs.
- **A general nix breakage in the guest.** A trivial `runCommand` derivation
  built fine in the same session where the workspace derivation failed instantly;
  `markdown`-lint and `clippy` derivations built normally minutes either side.
- **The consumer's own changes.** Reproduced with the agent's diff stashed.
- **systemd sandboxing on the agent unit.** No `ProtectSystem`/`PrivateMounts` on
  `katsuobushi-agent.service`, so this is a real system-wide mount, not a service
  namespace artefact.

## Possibly the same root, possibly separate

In the **same high-concurrency stretch**, instances also failed in ways that were
not nix at all:

- an agent harness **wedged** — a turn delivered but never begun, surviving three
  resends and the guest's own re-injections;
- **`transport dead — no heartbeat for 30s`** on three separate instances,
  including one mid-`--redeliver`;
- one reviewer **accepted a turn and never started it** — `turnId: 1`,
  `lastActivityAt == acceptedAt`, no reports for **3h 18m**;
- one dispatch **booted a VM that never received its directive** (`turnId: null`,
  `phase: idle`, `directive.md` intact on disk, `--redeliver` then hitting a dead
  transport).

These may be independent bugs. They are noted here because they clustered in the
same window as the nix faults, under the same load, which is at least consistent
with host resource pressure (load average 25 on 32 cores, four 8-vCPU guests plus
host builds).

## The experiment that would settle it

Two runs, ten minutes:

1. Build in a guest with the host **completely idle** — expect green.
2. Deliberately run a host `nix build` against a **live** guest build — expect
   one of the four strings above.

If (2) reproduces and (1) does not, the contention story is demonstrated rather
than merely well-fitting, and the fix direction is about isolating guest reads
from host writes on the shared store rather than about the sandbox's own setup.

## Acceptance criteria

- [ ] The experiment above is run and its result recorded
- [ ] If contention is confirmed, a mitigation is chosen — e.g. snapshotting the
      host store for the guest rather than sharing it live, a different 9p cache
      mode, or documenting that host builds must not run during guest builds
- [ ] If it is not confirmed, the four error strings are diagnosed on their own
      terms
- [ ] Consumers get a way to tell a real gate failure from this one — today an
      agent cannot distinguish "my change broke the build" from "the sandbox
      failed to construct", and the honest ones burn a turn reporting blocked
