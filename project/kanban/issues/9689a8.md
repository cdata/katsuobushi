## What to build

A repo that has never heard of heartbeats still gets the protection. The library
ships its own heartbeats inside the VM image, as ordinary files in the same
format that a project uses. A project's `.katsuobushi/heartbeats/` directory
**adds** to the shipped set. It never replaces it.

The shipped set covers the local work that every observed stall actually was:

- **`agent-work`** — the `katsuobushi-agent` cgroup consumed CPU since the last
  beat.
- **`nix-build`** — the `nix-daemon` cgroup consumed CPU since the last beat.

Both matter. One cold build through `nix develop` runs the agent under
`systemd.services.katsuobushi-agent` and its derivations under
`nix-daemon.service`, so the work of one build appears in two cgroups.

These files are what people copy, so they are also the worked examples. Shell
inside a block scalar is indented, and that is the usual source of a check that
passes and means nothing. The shipped files must show the indentation and the
exit-status rule clearly.

An operator who asks why a VM is `active` must be able to read the answer out of
a file inside the VM, not out of Rust.

## Acceptance criteria

- [ ] A workspace with no `.katsuobushi/heartbeats/` directory still reports
      `active` for the length of a cold build.
- [ ] The shipped heartbeats are readable files inside the VM, in the same
      format a project uses.
- [ ] A workspace with one heartbeat of its own still runs the shipped set —
      both a shipped heartbeat and a project heartbeat appear in the state.
- [ ] `agent-work` beats while the `katsuobushi-agent` cgroup burns CPU.
      `nix-build` beats while the `nix-daemon` cgroup burns CPU.
- [ ] Each shipped file carries a comment showing the block-scalar indentation
      and the exit-zero rule.
