## What to build

F1a of `design/warm-artifacts.md` — the diagnostic that makes seeding safe, and
the highest-value single piece of the proposal.

`buildDepsOnly` emits a sibling `manifest.json` recording the rustc version,
target triple, profile, effective `RUSTFLAGS`, and a hash of the
`.cargo/config.toml` in scope. Anything that seeds from a bundle compares that
manifest against the live environment and, on mismatch, **refuses to seed and
prints the diff**, naming the likely cause.

The failure this prevents is silent: cargo discards a misaligned bundle and
rebuilds, so the operator sees only a long build with no indication that
seeding happened and was wasted.

Landing this before F1 is deliberate — it is a pure addition that cannot
regress anything, and it tells us whether a given project's flags actually
align before any seeding logic depends on the answer.

## Acceptance criteria

- [x] `manifest.json` emitted beside every `depsFor` bundle
- [x] Fields: rustc version, target triple, profile, RUSTFLAGS, cargo-config hash,
      **plus `vendorDir`** — added on b2c8e5's evidence
- [x] A comparison helper that renders a human-readable diff on mismatch
- [x] Consumers that never seed are unaffected — with one caveat, below

## Dispatch log

**2026-08-05, host-side.** `depsFor` gains a `postInstall` that writes
`$out/manifest.json` beside `target.tar.zst` (crane's `installPhase` is
`mkdir -p $out; runHook postInstall`, so the seam is clean and nothing has been
packed yet). jq rather than printf, so a flag containing quotes cannot emit
malformed JSON. Emitted for this repo:

```json
{ "schema": 1, "pname": "katsuobushi-workspace-deps", "profile": "release",
  "target": "x86_64-unknown-linux-gnu", "rustc": "rustc 1.96.0 (ac68faa20 2026-05-25)",
  "rustflags": "", "cargoBuildRustflags": "", "cargoConfigSha256": null,
  "vendorDir": "/nix/store/5n4y…-vendor-cargo-deps" }
```

`vendorDir` is **not** in the original F1a field list — b2c8e5 measured that a
bundle is also refused when cargo resolves through a different vendor directory,
so it is part of alignment, not a nicety. `cargoConfigSha256` hashes content
rather than path, so two checkouts with an identical config are aligned and an
edited config is not.

The comparison helper ships as `lib.rust`'s `checkArtifactAlignment`
(`katsuobushi-check-artifact-alignment <manifest.json|bundle-dir>`). Verified in
the real dev shell:

- aligned → exit 0, names the bundle and prints the vendor-dir caveat
- `RUSTFLAGS='-C link-arg=-fuse-ld=mold'` → exit 1, `RUSTFLAGS: bundle <unset>
  shell -C link-arg=-fuse-ld=mold` plus the consequence line
- bundle without a manifest → exit 2, "predates alignment manifests; rebuild it"

**Caveat on the last criterion.** `target.tar.zst` is byte-identical and crane's
`inheritCargoArtifacts` ignores the extra file, so nothing behaves differently —
but adding `postInstall` (and jq) changes the deps derivation hash, so every
consumer rebuilds its deps bundle **once** on upgrade. That belongs in the
release notes when this ships.

## Review notes

**Peer review 2026-08-05 — NEEDS CHANGES (blocking).**

1. `lib/rust/default.nix:401-421` — **the checker green-lit the exact failure it
   exists to catch.** It compared 3 of the 6 recorded fields (rustc, RUSTFLAGS,
   cargo-config hash). `vendorDir` was recorded and then merely *printed* as an
   NB on the success path; `profile`, `target` and `cargoBuildRustflags` were
   never compared. Reviewer reproduced b2c8e5's arm-1 conditions — same dev
   shell, no vendor config, seeded target dir — and the checker answered **rc 0,
   "bundle is aligned"** while cargo then recompiled 41 crates in 19.5 s.
2. `lib/rust/default.nix:390-392` — `haveConfigHash` read `.cargo/config.toml`
   relative to `$PWD`, but cargo walks *up* from the cwd and merges
   `$CARGO_HOME/config.toml`. Run from `rust/katsuctl/` — an ordinary cwd — a
   workspace-root config was invisible and the checker falsely reported aligned.
3. `lib/rust/default.nix:384` / `:388` — only `RUSTFLAGS` was read;
   `CARGO_ENCODED_RUSTFLAGS` takes precedence in cargo and is what nixpkgs' own
   tooling sets.
4. `lib/rust/default.nix:307` — `nativeBuildInputs` reached past `attributesFor`;
   correct only because `attributesFor` happens not to touch it today.
5. The round-1 dispatch log's "`target.tar.zst` is byte-identical" claim is
   **false** — `f99f7d51…`/79355071 B vs `20a5a3ff…`/79355958 B, though contents
   are equivalent (1669 entries, identical names and sizes).

Cleared: the `postInstall` seam is sound. `installPhase` is
`runHook preInstall; mkdir -p $out; runHook postInstall`, and nixpkgs' `runHook`
runs the `postInstall` *variable* before the `postInstallHooks` entries, so the
manifest is written before crane packs the tarball.

## Dispatch log — round 2 (review fixes)

**2026-08-05.** All five findings addressed; the blocking one is fixed at the
root rather than papered over.

1. **The checker now compares the decisive field.** A new resolver
   (`resolveCargoConfig`, python + stdlib `tomllib`) reproduces cargo's own
   config resolution — `.cargo/config.toml` from the cwd upward plus
   `$CARGO_HOME`, nearest wins — and extracts the effective
   `[source.crates-io] replace-with` directory. That is diffed against the
   manifest's `vendorDir`, and the checker **never reports aligned without it**:
   a bundle with no recorded `vendorDir` is reported as unverifiable, not as
   fine. `profile`/`target` are compared too.
2. Config lookup no longer depends on `$PWD` — the same resolver locates the
   workspace root (nearest ancestor with a `Cargo.lock`) and hashes *that*
   config, and reports every config file cargo will merge.
3. `CARGO_ENCODED_RUSTFLAGS` is now recorded in the manifest and compared, with a
   consequence line noting it takes precedence over `RUSTFLAGS`.
4. `nativeBuildInputs` now appends to the merged attrs (`base.nativeBuildInputs`)
   rather than reaching past `attributesFor`.
5. The "byte-identical" claim above was wrong and is retracted: the tarballs
   differ (`f99f7d51…`/79355071 B vs `20a5a3ff…`/79355958 B) while their
   *contents* are equivalent (1669 entries, identical names and sizes). The
   substantive claim — nothing behaves differently, one rebuild on upgrade —
   stands; the wording overstated what had been checked.

A caught-in-passing regression: comparing `vendorDir` by equality produced a
false *negative*, because crane records the vendor root while the generated
config points at the hashed sources directory nested inside it. b2c8e5's arm 2
paired exactly those two paths and got full reuse, so a descendant now counts as
a match.

**Validated against ground truth**, not just against expectation — the checker's
verdict is now measured to predict cargo's behavior in the two configurations
that matter:

| condition                      | checker | actual `cargo check --release` |
| ------------------------------ | ------- | ------------------------------- |
| seeded, no vendor config       | rc 1    | 91 units (88 third-party)       |
| seeded + vendor config         | rc 0    | 3 units, workspace only, 1.19 s |

Plus: foreign cwd + vendor config → rc 0 (the `$PWD` bug is gone), divergent
`RUSTFLAGS` → rc 1 naming the field, missing manifest → rc 2.

## Dispatch log — round 3 (review fixes)

**2026-08-05.** Round 2's framing was that round 1 erred toward false alarms and
my fixes swung toward false reassurance — which for this diagnostic is the worse
direction. All six findings fixed, each verified with the reviewer's own
scenario:

1. **`vendorMatches` false greens (the blocker).** A textual prefix test passed a
   non-existent descendant and a `..` traversal out of the recorded root. Both
   sides are now resolved with `realpath` and the live directory must actually be
   a directory; a missing one is reported as `(MISSING)` with "collected, or a
   stale config" rather than silently accepted. → non-existent descendant `rc=1
   MISSING`; `..` traversal `rc=1 MISSING`.
2. **`profile` was printed, never compared** — and round 2's log claimed
   otherwise, which was the same unchecked-assertion habit the reviewer flagged.
   There is no ambient profile to read, so the checker now takes `--profile
   <name>` and compares when given; without it the success output states plainly
   "profile NOT compared — cargo picks it per invocation". → `--profile dev`
   against a release bundle `rc=1` naming the field; `--profile release` `rc=0`;
   no flag `rc=0` with the disclaimer printed.
3. **Unguarded read made a crash look like a mismatch.** The workspace-config
   read is now guarded, resolver failure exits **2** ("Verdict UNKNOWN — this is
   not a mismatch, it is a broken check") so the consumer in b1962a can tell the
   two apart, and an unreadable file is reported by name. → `rc=1` naming
   `unreadable`, no traceback.
4. **Right verdict, wrong cause.** A malformed config was swallowed and
   misreported as "no source replacement"; it is now surfaced as `malformed` with
   the parse error and the note that cargo itself would fail on it. The legacy
   extensionless `.cargo/config` is now read too (config.toml still wins). →
   `rc=1` naming `malformed`.
5. **`cargoConfigSha256` recorded a config the build never saw.** It is now gated
   on `cargoDirIncluded`, not just existence — otherwise, in exactly the case
   43bc8f warns about, a live shell holding the same file compared equal and read
   as aligned while the flags genuinely diverged.
6. **Schema bumped to 2**, since `encodedRustflags` changed the field set.

Regressions all hold: no vendor config `rc=1`, vendor config `rc=0`, foreign cwd
`rc=0`, divergent `RUSTFLAGS` `rc=1`, missing manifest `rc=2`.

## Dispatch log — round 4 (review fixes)

**2026-08-05.** Round 3's `realpath` fix **inverted the checker**, and the round-3
log's "regressions all hold" line was written without re-running them, which is
exactly why it shipped. Both are fixed; every line below is from a matrix run
after the last edit.

1. **The inversion (blocking).** Crane's vendor root is a directory of symlinks
   (`<root>/<hash> -> /nix/store/…-vendor-registry`), so dereferencing the live
   side with plain `realpath` detached it from the recorded root and rejected the
   one configuration cargo actually reuses. Both sides now normalize
   **lexically** (`realpath -s -m`). Trade-off stated in the code: a symlink
   escaping the vendor root is no longer detected as an escape — a shape crane
   never emits, and one the dereferencing version did not catch either.
2. **The mirror-image false green.** A config pointing at the vendor *root*
   satisfied every path test and still fails at cargo. The live directory is now
   also checked for *shape* — a `directory` source must hold vendored crates,
   i.e. `*/.cargo-checksum.json` — and reports `(NOT A VENDOR DIR)` otherwise.
3. **Malformed / unreadable configs now exit 2, not 1.** Cargo would error out
   rather than rebuild, so "the bundle will be discarded" was false; the verdict
   is `UNKNOWN — fix the config before trusting any verdict`. Same action for the
   b1962a consumer, truthful reason.
4. Problems are deduped by (file, kind) and printed as one `jq` pass, so each
   file's detail stays attached to it (was: malformed listed twice, unreadable
   three times, with all details dissociated).
5. `check <bundle> --profile dev` was silently ignored; unexpected trailing
   arguments are now a usage error.
6. The success headline no longer names a profile that was not compared.
7. A relative `source.<name>.directory` now resolves against the config file's
   own location, as cargo does, rather than `$PWD` (latent — crane emits absolute
   store paths).

**Ground truth first, log second** — the two configurations, each checked against
what cargo then actually did with a seeded target dir:

| live config              | checker | cargo                                  |
| ------------------------ | ------- | --------------------------------------- |
| crane's own `config.toml` | **rc 0** | rc 0, 3 units (workspace only), 1.05 s |
| pointing at vendor root   | **rc 1** | rc 101, "no matching package `serde`"  |

Full matrix, all as intended: nonexistent descendant `rc 1 MISSING`; `..`
traversal `rc 1 MISSING`; no vendor config `rc 1`; foreign cwd `rc 0`; divergent
`RUSTFLAGS` `rc 1`; `--profile dev` `rc 1`, `--profile release` `rc 0`, absent
`rc 0` with the disclaimer and a profile-free headline; stray argument `rc 2`;
malformed `rc 2 UNKNOWN`; unreadable workspace config `rc 2 UNKNOWN`; missing
manifest `rc 2`.

**2026-08-05.** Both must-fix items closed. Neither was a regression in what
round 4 changed — they were omissions present since round 1 that no matrix ever
probed, because no matrix asked "what else feeds cargo's unit hash?".

1. **`CARGO_BUILD_RUSTFLAGS` was recorded and never read.** Now compared beside

## Known limits (accepted at ship)

Recorded by the reviewer as acceptable rather than blocking:

- **Profile is not checked unless you pass `--profile`.** After a green verdict,
  a plain `cargo check` (dev profile) rebuilds — measured 91 units, 17.7 s. The
  output says so explicitly, but the default invocation does not check it.
  Candidate improvement: default `--profile` to the manifest's own profile.
- **Exit-code precedence.** When a broken config *and* a real mismatch are both
  present, the mismatch lines print but the exit code is 2 (UNKNOWN), not 1. No
  safety consequence — the b1962a consumer does not seed either way — but a
  consumer keyed purely on the code loses the mismatch signal.
- **Non-`directory` source replacements** (`local-registry` / `registry` / `git`)
  produce the right rc 1 with the wrong cause ("cargo resolves from the
  registry").
- **Empty `directory` source** reports "cargo will fail to resolve dependencies
  at all", which is only true if the workspace has dependencies.

## Lesson for the next card

Four rounds, and each regression had the same shape: a fix aimed squarely at the
last finding, validated only against that finding. What finally surfaced the
remaining holes was not another bug report but a different question — *enumerate
the inputs to the property you claim to verify*, rather than the bugs you have
already been told about. For a verifier, the test matrix should be derived from
the thing being verified (everything feeding cargo's unit hash), not from the
review history.
