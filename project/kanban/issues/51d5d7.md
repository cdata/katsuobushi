## What to build

The runner. The guest runs every heartbeat in the set and records, for each one,
whether it beats and for how long it has beaten.

The rules:

- A heartbeat runs as the agent user, with the workspace as its working
  directory.
- The guest runs the `check` body at that heartbeat's `interval`. Exit zero
  means the heartbeat beats. Any other exit code means it does not.
- The guest bounds each run by that heartbeat's interval. A check that outlives
  its interval is killed and does not beat.
- A heartbeat's **duration** counts from the first beat of an unbroken run. One
  failed check ends the run, and the next beat starts a new one.
- A heartbeat is **late** when its duration passes its own `timeout`. There is
  no universal ceiling. This card computes the flag; a later card acts on it.
- The `detail` body runs beside a beating check. Its first line of output
  narrates the beat. A `detail` body that fails is ignored, and the label alone
  shows.
- A file the guest cannot read or parse never beats. The guest reports the error
  to the host **once**, so a broken heartbeat is visible and is not silent.

## Acceptance criteria

- [ ] A check that exits zero beats. A check that exits non-zero does not.
- [ ] A check that sleeps past its own interval is killed and does not beat.
- [ ] A heartbeat's duration counts from the first beat of an unbroken run, and
      resets after one failed check.
- [ ] A heartbeat whose duration passes its `timeout` carries a late flag.
- [ ] A `detail` body's first line of output is attached to the beat. A `detail`
      body that fails leaves the beat intact with its label alone.
- [ ] A file that will not parse contributes nothing to the set, and its error
      reaches the host exactly once — not once per interval.
- [ ] The beat and duration logic is decided in a pure core and unit-tested
      without timers, BDD-named — e.g.
      `it_resets_the_duration_after_a_failed_check`,
      `it_flags_a_heartbeat_past_its_own_timeout`.

## Review notes

### Round 1 — `review-51d5d7-b5804fc3` — VERDICT: needs-changes

Gates verified by the reviewer: 29 lib + 33 server tests pass, clippy clean.
**0 tests exist for `runner.rs`.**

**Passed:**

- **Pure-core split.** `apply_check` (`heartbeat.rs:242-277`) is genuinely pure
  — injected time, no syscalls, no side effects. The 11 `beat_tests` pin every
  state-machine case. No decision logic leaked into the async runner.
- **Concurrency.** One task per heartbeat, no shared mutable state,
  `MissedTickBehavior::Delay` prevents pile-up. No races.

**Findings:**

1. **Kill path leaks grandchildren — `runner.rs:95-106`.** `child.kill().await`
   SIGKILLs `sh` and reaps it, so no zombie. But the shell's *grandchildren* are
   not killed; they reparent to PID 1. For a daemon running a timing-out check
   every interval, that is **one orphan per interval, unbounded**. Shipped
   library heartbeats (`pgrep`, cgroup reads) are leaf commands and won't
   trigger it, but heartbeat bodies are user-authored by design — `curl … && …`
   or `sleep 999` leaks forever. `spawn_detail` (`runner.rs:113-138`) uses
   `kill_on_drop(true)` and has the same blind spot. Needs a process-group kill
   (`Command::process_group(0)`, then `kill(-pgid, SIGKILL)`) or an explicit
   documented constraint that check bodies must be leaf commands.
2. **`KATSU_WORKSPACE` is scope creep with a silent failure mode —
   `server.rs:1039-1046`.** The env var is invented here; it appears in no PDD
   and no existing env-var schema. The design only says the workspace is the
   working directory, which the launcher already provides. Worse, if
   `current_dir()` fails, `unwrap_or_default()` yields an empty `PathBuf`, so
   `hb_dir` degrades to the relative `.katsuobushi/heartbeats` and checks run
   against whatever the OS resolves — **with no log line at all**. An operator
   cannot diagnose this from logs.
3. **Two named acceptance criteria are untested.** (a) The kill path has zero
   tests despite being the most OS-sensitive code in the change. (b) "a detail
   body that fails leaves the beat intact with its label alone" is tested only
   on the pure-core side; nothing verifies that a failing `spawn_detail`
   actually yields `Beat{detail: None}` in `run_one`.

**Noted, deliberately out of scope:** errors are reported once by loading the
heartbeat set only at startup. The letter of the contract is satisfied, but a
heartbeat file added or fixed after start is invisible until restart. The
reviewer judged this an acceptable boundary for this card. Filed separately.

### Round 2 — `review-51d5d7-b5804fc3` — VERDICT: accept

Gates observed by the reviewer: 31 lib + 33 server tests pass, clippy clean.

1. **Kill path — FIXED, and the repair itself was audited.** `process_group(0)`
   makes the shell its own group leader, so PGID equals its PID. `child.id()` is
   read immediately after spawn; on timeout the `child.wait()` future is dropped
   **without reaping**, so the kernel cannot recycle that PID — meaning
   `kill(-pgid)` provably cannot hit an unrelated process group. No reuse
   window. The `unsafe` block is sound (`libc::kill` takes only integers, so no
   memory-safety obligation); ignoring the return is fine since `ESRCH` is the
   only interesting error and the timeout path reaps and returns `false`
   regardless. The `spawn_detail` restructure holds up: the drain task runs
   concurrently with `child.wait()` so the pipe cannot fill and stall the child,
   and the task is always either awaited or aborted — no task leak traded for
   the process leak, no deadlock path found. Children are reaped on both the
   timeout and normal paths. `libc` added only to the guest crate's deps; zero
   new `Cargo.lock` entries.
2. **`KATSU_WORKSPACE` — FIXED.** `git grep` across the tip returns nothing. The
   reviewer endorsed `expect()` on `current_dir()`: the call sits in `main()`
   before any `tokio::spawn`, so it crashes the whole server with an actionable
   message, and a subsystem with no valid working directory cannot function at
   all — loud beats silent degradation.
3. **Tests — PARTIALLY FIXED, accepted.**
   `it_returns_none_when_the_detail_body_exits_nonzero` is complete and
   deterministic. `it_returns_false_and_kills_the_process_group_when_the_check_times_out`
   **overclaims in its name**: it asserts only the boolean return, never that
   grandchildren actually died. Proving that would need the check to record a
   grandchild PID and then inspect `/proc`. Accepted as a return-value
   regression marker because the mechanism itself was proved correct above, but
   the coverage gap is real and the name is misleading.

No regression in the previously passed items. Zero changes under `project/`.

**New minor finding, no action taken:** on `spawn_detail`'s success path,
`drain.await.unwrap_or_default()` swallows a drain-task panic and yields an
empty `Vec`, so the beat would silently show as having no detail output. Very
unlikely (it only reads a pipe) and invisible to an operator if it ever happens.
