## What to fix

The auto-nudge budget cannot span a real cold build, so an agent that
backgrounds a build and yields is lost permanently.

With the shipped defaults the entire recovery window is **~91 seconds**:

```
stopGraceMs     = 1500    # lib/sandbox/default.nix
maxNudges       = 3
nudgeIntervalMs = 30000
```

`1.5s + 3 × 30s ≈ 91s`. A project whose cold compile is 15–25 minutes — the
case `progressStallSecs`' own doc comment describes — exhausts every nudge
inside the first two minutes of a twenty-minute build. The turn resolves
`ended-unreported`, and when the build finishes nothing re-prompts the agent.
It sits idle, holding its slot, until an operator notices and prompts by hand.

### Observed

One `arcanabasis` session lost four agents this way, from ~10 minutes to just
over **3 hours** each. The journal of `review-b48620-7e2487f2` shows the
mechanism exactly — the three nudges land ~30s apart and the turn is resolved
90 seconds after it ended, while the build it was waiting on had ~18 minutes
left to run:

```
12:11:08  working   Waiting on background debug-test build and text_probe compile
12:11:41  working   Still waiting …                          <- nudge 1  (+33s)
12:12:07  working   Debug test archive is compiling …         <- nudge 2  (+26s)
12:12:44  working   Still compiling …                         <- nudge 3  (+37s)
12:13:27  re-armed  turn 1 ended without a terminal report    <- budget spent
   …      (silence)
15:58     host operator prompts by hand
```

Every liveness signal looked healthy throughout: `streamActive: true` and a
heartbeat current to the second, while `lastActivityAt` was three hours stale.
`sandbox status` reported `ended-unreported`, which is accurate but reads the
same for "stalled forever" as it does for "working hard and quiet".

### Three things compound

1. **The knobs are not consumer-facing.** `maxNudges` and `nudgeIntervalMs` are
   plain local bindings in `lib/sandbox/default.nix` (~`:265-266`), not
   function arguments — unlike `progressStallSecs ? 300` beside them. A
   consumer who diagnoses this exactly still cannot widen the window without
   patching the library.

2. **The consumer already declared the answer and nothing reads it.**
   `arcanabasis` sets `progressStallSecs = 1500`, precisely as the lib's own
   comment advises for "a ~20-minute build". So the project has already stated
   its build reality to one subsystem; the subsystem responsible for recovering
   stalls never consults it. The nudge budget covers ~6% of the window the
   consumer declared.

3. **The nudge text sanctions the behaviour that kills the agent.** It reads:

   > "if you are waiting on a background command, wait for it to finish and
   > verify it, then `report done`"

   An agent that complies checks the build, sees it still running, reports
   `working`, and yields again — spending a nudge without progress. All three
   are consumed by the agent doing exactly what it was just told.

## Options

Deliberately left open; the tradeoffs differ and more than one may be worth
taking together.

- **Bounded exponential backoff** (short-term favourite). Keep a hard cap but
  let the interval grow — e.g. 30s, 1m, 2m, 4m, 8m, 16m spans ~31 minutes in
  six nudges instead of 90 seconds in three. Cheap, no protocol change, still
  bounded so a genuinely dead agent still resolves. Still polling.

- **Derive the budget from `progressStallSecs`.** The consumer has already
  declared its cold-build time; nudge until some multiple of it, then resolve.
  Adds no new configuration and makes the two subsystems agree by construction.

- **Expose the knobs as consumer arguments.** Smallest possible change, but
  pushes tuning onto every consumer and leaves the default wrong for exactly
  the projects the sandbox is most useful for.

- **Stop polling: resolve on idleness, not on a timer.** The turn is only
  genuinely dead when the agent has no work in flight. If the guest can observe
  that the agent's session still has live children (the backgrounded build),
  it can hold the turn open rather than counting down, and re-prompt when the
  session actually goes quiet. Converts a blind timer into a real signal.

- **Stop polling: an event when background work completes.** `HookEvent`
  already carries `SessionReady` / `TurnAccepted` / `TurnEnded`. A fourth event
  raised when a backgrounded command finishes would let the guest re-prompt on
  the real edge instead of guessing. Needs the harness to surface it, so it is
  the largest change — but it is the only option that removes the guesswork
  rather than widening it.

- **Fix the nudge text regardless.** Whichever of the above lands, the current
  wording should stop endorsing "wait for it to finish" from inside a yielded
  turn. But see the correction below — it must *not* be replaced with "run it
  in the foreground", because the agent cannot.


## Correction — the obvious workaround does not exist

An operator instructed several agents to "run every build in the foreground so
the turn never ends", and a reviewer reported back:

> "cargo test --workspace exceeded the 120s foreground timeout and was
> auto-moved to background by the tool"

**The agent harness auto-backgrounds any command exceeding ~120 seconds.** No
real build of a Bevy workspace finishes inside that, so an agent *cannot* keep
a build in the foreground however it is instructed. Every agent that runs the
project's own test or lint command is therefore forced into the
background-and-yield pattern, and the ~91-second nudge budget guarantees the
turn is lost.

That reframes the whole issue:

- It is **not** an agent-discipline problem with a prose fix. The behaviour is
  structural, and no wording in `nudge_text` or in a project's dispatch
  instructions can route around it.
- The agent in question did everything right — it posted `working` every ~30s
  while waiting, and even armed its own watcher — and was still resolved
  `ended-unreported` and lost. Diligence does not help.
- So the fix has to be on the katsuobushi side: a budget that can span a real
  build, or a signal that does not depend on the turn staying open.

This also raises the priority of the two non-polling options above. If a turn
that yields to a >120s command is *the normal case* rather than an agent error,
then resolving on genuine idleness — or on an event when the backgrounded
command completes — stops being an elegant refinement and starts being the
correct design.

### Seam

- Constants: `MAX_NUDGES_DEFAULT` / `NUDGE_INTERVAL_MS_DEFAULT` in
  `rust/katsuobushi-sandbox-protocol/src/lib.rs` (`:154`, `:161`).
- Nix bindings + env plumbing: `lib/sandbox/default.nix` `:265-266` and
  `:1138-1139` (`KATSU_MAX_NUDGES`, `KATSU_NUDGE_INTERVAL_MS`).
- Decision logic: the pure core behind `spawn_grace` in
  `rust/katsuobushi-sandbox-guest/src/bin/server.rs` — the module doc at `:36`
  describes the loop, and the nudge counter is documented at `:135`.
- Nudge wording: `nudge_text` (`server.rs:591`).
- The backoff schedule belongs in the pure core so it is unit-testable without
  the timer, matching how the existing nudge decision is already factored.

## Acceptance criteria

- [ ] An agent that backgrounds a 20-minute build and yields is still
      re-promptable when that build finishes, under the shipped defaults
- [ ] The recovery window is bounded — a genuinely dead agent still resolves
      as `ended-unreported` rather than being nudged forever
- [ ] A consumer can influence the window without patching the library, or the
      window is derived from configuration the consumer already supplies
- [ ] `nudge_text` no longer instructs a yielded agent to wait on a background
      command
- [ ] The schedule is decided in the pure core and unit-tested without timers,
      BDD-named — e.g. `it_backs_off_between_successive_nudges`,
      `it_stops_nudging_at_the_cap`,
      `it_spans_a_cold_build_before_resolving_unreported`
