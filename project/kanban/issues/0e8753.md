## What to build

One heartbeat is not a file. It beats for exactly as long as a turn is in
flight. The turn-accepted hook arms it and the stop hook silences it.

This heartbeat lives in the guest because the guest is the one party that knows
turn state. It buys two properties for free:

- An agent that reads files and thinks is `active`, not `idle`.
- A turn that never ends beats past its timeout and becomes late, which names a
  wedged harness.

Its timeout is 60 minutes. A single turn longer than an hour is a fault worth
saying out loud.

It joins the same set as the file heartbeats and obeys the same beat and
duration rules.

## Acceptance criteria

- [ ] An agent that reads files and calls no build reports `active` for the
      length of its turn, with no other heartbeat beating.
- [ ] The heartbeat stops when the stop hook fires.
- [ ] A turn in flight for longer than 60 minutes raises the late flag.
- [ ] The arm and silence transitions are unit-tested without timers,
      BDD-named — e.g. `it_beats_while_a_turn_is_in_flight`,
      `it_goes_late_after_sixty_minutes`.

## Review notes

### Round 1 — `review-0e8753-849fefd0` — VERDICT: accept

Gates observed by the reviewer: 74 guest tests, 447 controller tests, clippy
clean on both.

**Arm/silence edge cases, all checked and all safe:**

- `TurnEnded` with nothing armed no-ops — the silence is guarded by the
  presence of a turn (`server.rs:424`). No underflow, no panic.
- Two `TurnAccepted` back to back are idempotent (`server.rs:405,371`) and the
  duration does **not** reset — it keeps counting from the first tick after arm,
  which is correct for "beats for exactly as long as a turn is in flight".
- `TurnEnded` carries no turn id **by design** — the stop hook fires for
  whatever turn is current, and turns never run concurrently, so any
  `TurnEnded` silencing the current turn is correct rather than a missing check.
- The `Relaxed` ordering is sufficient: the `AtomicBool` is the only shared
  state, nothing else needs publishing alongside it, and `Relaxed` stores are
  never indefinitely hidden. Worst-case over-run is one tick (10s), so this
  design **cannot** manufacture the wedged-harness condition the heartbeat
  exists to detect. `Release`/`Acquire` would be more self-documenting but is
  not required for correctness.
- 60-minute timeout confirmed (`TIMEOUT_SECS = 3600`, `heartbeat.rs:224`) and
  the late flag comes from the same shared `apply_check` the file heartbeats
  use — no parallel reimplementation to drift.

Server tests do exercise real `Session::step` transitions rather than setting
`Outcome` fields directly, so they are not rubber-stamp.

**Observations carried forward, filed separately:**

1. `run_turn_heartbeat` sets `beat.armed` directly and calls `tick()`; it never
   calls `arm()` or `silence()` (`runner.rs:59-60`). So `arm()`'s doc claim
   that it records `beat_started` "so duration is measured from the turn's first
   activity" is **not true in production** — `beat_started` is set at the first
   tick after the flag flips, up to 10s late. Immaterial against a 60-minute
   timeout, but it means the five `TurnBeat` unit tests exercise an API
   production does not use.
2. Two missing tests: `TurnEnded` before any `TurnAccepted`, and nothing
   verifying `execute_outcome` actually performs the `store(true)`/`store(false)`
   (`server.rs:550-555`).

**Acceptance criterion 1 ("with no other heartbeat beating") cannot be verified
end-to-end yet** — the work-state combination is explicitly deferred to
`a91d4c`, and `beat.tick()`'s status is discarded at `runner.rs:60` for now.
Not a fault of this card.
