## What to build

`spawn_check` and `spawn_detail` build their children without `kill_on_drop`.
That is fine on the paths those functions control: a check that outlives its
budget is killed by process group, and card `51d5d7` was bounced specifically to
make that kill cover grandchildren.

Card `612108` added a second way for those futures to end. A heartbeat file that
is deleted or edited into a syntax error now has its task `abort()`ed. Tokio
delivers the abort at the next await point, and one of those await points is
`timeout(budget, child.wait())` inside `spawn_check`. When the abort lands there
the `Child` is dropped without being killed, so the `kill_pgroup` call is never
reached and the shell plus any grandchildren of a user-written pipeline survive
as orphans.

The peer reviewer on `612108` measured the blast radius and accepted it: at most
one orphaned child, living at most one budget duration, in its own process group
where it cannot reach the guest. That is a large improvement on the previous
behaviour, which was a task that never stopped at all. It is still a hole in a
guarantee the project already paid to close once.

`kill_on_drop(true)` on both command builders closes it, because a dropped
`Child` then kills its process. Confirm it composes with the existing
`process_group(0)` and the explicit `kill_pgroup` on timeout rather than
conflicting with them.

## Acceptance criteria

- [ ] `spawn_check` and `spawn_detail` set `kill_on_drop(true)`.
- [ ] A task aborted while its check is running leaves no orphaned process.
- [ ] The existing timeout path still kills the whole process group, and its test
      still passes unchanged.
- [ ] `nix develop -c rust lint` is clean.
