## What to build

`spawn_check` and `spawn_detail` build their children without `kill_on_drop`.
That is fine on the paths those functions control: a check that outlives its
budget is killed by process group, and card `51d5d7` was bounced specifically to
make that kill cover grandchildren.

Card `612108` added a second way for those futures to end. A heartbeat file that
is deleted or edited into a syntax error now has its task `abort()`ed. Tokio
delivers the abort at the next await point, and one of those await points is
`timeout(budget, child.wait())` inside `spawn_check`. When the abort lands there
the `Child` is dropped without being killed, so the `kill_pgroup` call is never
reached and the shell plus any grandchildren of a user-written pipeline survive
as orphans.

The peer reviewer on `612108` measured the blast radius and accepted it: at most
one orphaned child, living at most one budget duration, in its own process group
where it cannot reach the guest. That is a large improvement on the previous
behaviour, which was a task that never stopped at all. It is still a hole in a
guarantee the project already paid to close once.

`kill_on_drop(true)` on both command builders closes it, because a dropped
`Child` then kills its process. Confirm it composes with the existing
`process_group(0)` and the explicit `kill_pgroup` on timeout rather than
conflicting with them.

## Acceptance criteria

- [ ] `spawn_check` and `spawn_detail` set `kill_on_drop(true)`.
- [ ] A task aborted while its check is running leaves no orphaned process.
- [ ] The existing timeout path still kills the whole process group, and its test
      still passes unchanged.
- [ ] `nix develop -c rust lint` is clean.

check, records its PID, aborts the task and verifies via `kill(pid, 0)` that the
process is gone.

Host verified the merged tree: `nix develop -c rust test` passes **577**
(459 + 62 + 46 + 10). The implementor reported "118 tests across the three
crates", which is a per-binary subtotal rather than the workspace figure — the
fourth such undercount this session.

**Concern referred to the reviewer.** The new test's check body is
`echo $$ > pidfile; sleep 60`. `$$` is the **shell's own** PID, and because the
body is two commands the shell forks for `sleep` rather than exec'ing into it —
so `sleep` is a *grandchild* with a different PID. The test therefore proves the
shell died, not that the grandchild did. That matters because tokio's
`kill_on_drop` sends `SIGKILL` to the child PID, **not** to the process group,
so the grandchild may still orphan on the abort path — which is precisely the
hole this card exists to close. This is the same shape as the weakness a
reviewer already found in `51d5d7`'s kill-path test.

## Review notes

### Round 1 — `review-850ce4-e442eb56` — VERDICT: needs-changes

Gates: 577 tests pass, lint clean.

**BLOCKING — the host's concern was correct, and the reviewer proved it with an
experiment rather than an argument.** It spawned `sh -c 'sleep 60 & wait'` in a
new process group, killed only the shell (PID 6088) to simulate `kill_on_drop`,
and observed the grandchild `sleep` (PID 6090) **survive with `ppid=1`** —
orphaned.

**And it explained why the new test passes anyway.** For the body
`echo $$ > pidfile; sleep 60`, the shell **execs into** `sleep` as its last
command (`ps` confirms PID 6057 shows `COMMAND=sleep` with no children), so
there is no grandchild to leak. The test passes by coincidence of the shell's
exec-into-last-command optimisation, not because grandchildren are cleaned up.
A real check body containing a pipeline or a background job still orphans.

So the second acceptance criterion — *"a task aborted while its check is running
leaves no orphaned process"* — is **not met**. `kill_on_drop` sends `SIGKILL` to
the child PID only; `process_group(0)` establishes the group but does not make
`Child::drop` kill it.

**Everything else is clean:**

- **No double-kill or race on the timeout path.** After `child.wait()` reaps the
  zombie, `child.id()` returns `None`, so `kill_on_drop`'s `Drop` calls
  `start_kill()`, gets `None`, and sends nothing.
- **The timeout test is bit-for-bit unchanged.**
- **`spawn_detail` loses no output** — the drain task is a separate
  `tokio::spawn`; killing the shell closes the pipe, the drain sees EOF and
  completes normally.
