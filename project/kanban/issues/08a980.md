## What to build

Move the landing step of the report bridge from `done` to `ready`.

The bridge today says: on `done`, `sandbox fetch`, land the branch, then set the
card to `needs-review`
(`plugins/katsuobushi/skills/project-orchestration/SKILL.md` lines 256-257). So
a change sits in the owner's history while a reviewer decides whether it is
correct, and a card that bounces three times lands four times.

The corrected bridge:

- **`done`** → `sandbox fetch card-<id>`, check that work actually landed on the
  branch, then `project status set <id> needs-review`. **No landing.** Pause the
  VM as it does now, and give the reviewer the branch.
- **review accepts** → the orchestrator lands the branch (card `7f46b9`), then
  `project status set <id> ready`.
- **review bounces** → the card returns to `in-progress` and nothing is landed.
  The next round adds commits to the same branch.

Before `ready`, the owner's history holds no part of the card. This gives three
properties worth stating in the prose: the owner's history holds only reviewed
work, a bounce costs no landing, and "has this landed" has an exact answer
because the card says so.

The owner still accepts a `ready` card. That gate does not move. A returned
`ready` card now needs a revert, and the retained branch is what the revert
uses — say so.

Check the `implement` skill and the sandbox skill for the same
`done`-then-land ordering and correct them together.

## Acceptance criteria

- [ ] The report bridge lands nothing on `done`
- [ ] The owner's history is unchanged between `in-progress` and `ready` for a
      card that reaches `needs-review`
- [ ] A card that bounces twice and then passes adds exactly one commit to the
      owner's history
- [ ] The skills describe landing as the step that moves a card to `ready`, and
      nowhere else
- [ ] The prose says a returned `ready` card needs a revert, and names the
      retained branch as the revert artifact
- [ ] No other skill still tells the orchestrator to land on `done`
