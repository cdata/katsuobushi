## What to fix

A dispatched agent can end its turn with heavy work still running, and nothing
in the skills tells it not to. The next party pays for it.

Observed in `cdata/arcanabasis`: a reviewer VM was asked, during a warm-up
turn, to check its nix store health. It ran `nix-store --verify`, which came
back clean, and then started `nix-store --verify --check-contents` — a full
content hash of the store. It reported the situation accurately and then ended
its turn with that job **still running**:

> The deeper `nix-store --verify --check-contents` (full content hash of all
> 360G) was still running after 15+ minutes with near-zero I/O progress ... did
> not finish in this warm-up window and was left running in background

The store there is an overlay on a 1.9T shared read-only base with 360G used.
That job would have run for hours, on an 8-vCPU VM, while a second sandbox
compiled on the same host for the rest of the card. The orchestrator had to
notice and spend a turn killing it:

> KILLED: found the 'nix-store --verify --check-contents' job (pid 1158, pgid
> 1156) plus its wrapping bash shell ... Killed the whole process group

The agent did nothing dishonest — it was thorough and it said exactly what it
had done. It simply had no instruction that ending a turn with work running is
a problem, and no way to know another VM was sharing the host.

## Why it matters

Parallelism here is bounded by host cores, and the concurrency budget is
negotiated on the assumption that a paused or idle VM costs nothing. An agent
that leaves a job running silently breaks that arithmetic for every other party
in the session.

## What to fix

Add guidance to the guest contract, and to the `sandbox` skill's directive
advice:

- An agent should not end its turn with background work still running. Either
  wait for it, or kill it, and say which.
- If a check cannot finish inside a turn, say so and stop it, rather than
  leaving it to run unattended.
- A terminal report should state that nothing was left running.
- Orchestrators writing directives should ask for that confirmation, and the
  skill should show it in its example directive.

Worth pairing with a note that the guest's `/nix/store` is an overlay on a
large shared read-only base, so whole-store verification is never the right
tool inside a sandbox.

## Acceptance criteria

- [ ] The guest contract tells an agent not to end a turn with background work running
- [ ] The `sandbox` skill's directive guidance asks for explicit confirmation that nothing was left running
- [ ] The skill notes that the guest store is a shared read-only overlay, so whole-store verification is inappropriate there
- [ ] A worked example directive shows the confirmation being requested
