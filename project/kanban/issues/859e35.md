## What to build

`run_work_state_coordinator` keeps a `HashMap<String, BeatStatus>` of the latest
status per heartbeat label and never evicts from it. Every entry is trusted
forever.

If a heartbeat task stops sending — a panic, a dropped sender, any future change
that lets one of those loops exit — its final status stays in the map. When that
final status was `beating: true`, the combined work state stays `Active` for the
life of the guest. The peer reviewer on `f7de81` named this exactly: it is the
false-busy condition the whole heartbeat design exists to prevent, reintroduced
by the layer that reports the state.

Today the risk is small. `run_one` and `run_turn_heartbeat` are plain infinite
loops with their spawn failures handled, so neither realistically exits. That is
a property of the current code, not a guarantee of the design, and nothing tests
it or writes it down.

Give the coordinator a staleness bound. An entry that has not been refreshed
within some multiple of its heartbeat's own interval should stop counting toward
`Active` — a heartbeat that has gone silent is absent, which the design already
distinguishes from late.

## Acceptance criteria

- [ ] A heartbeat whose task stops sending stops holding the work state at
      `Active`.
- [ ] The staleness bound is derived from the heartbeat's own interval, not a
      single global constant, since intervals differ per heartbeat.
- [ ] A slow-but-alive heartbeat is never treated as stale — the bound must
      clear a normal late tick.
- [ ] The rule is decided in a pure core and unit-tested without timers,
      BDD-named.
- [ ] `nix develop -c rust lint` is clean.

## Review notes

### Round 1 — `review-859e35-7f169b1c` — VERDICT: accept

Gates observed by the reviewer: 581 tests pass, lint clean.

**The 3× multiplier clears the worst legitimate gap, with worked reasoning.**
The worst case between consecutive sends is exactly **2×** the interval — a
check filling its whole budget plus `MissedTickBehavior::Delay` adding another
full interval. The bound is 3× with a strict `>`, leaving a full interval of
margin. A slow-but-alive heartbeat cannot be marked stale, which was the
dangerous direction: reporting `idle` during a live build would be worse than
the bug this card fixes, and would let nudges fire into working agents.

- **The `tokio::select!` rewrite loses no messages** — when the ticker branch
  wins, the unselected `recv` leaves its message in the mpsc channel. A closed
  channel breaks rather than spinning.
- **Backward clock skew is safe** — `saturating_sub` returns 0 and `is_stale`
  returns false, so an NTP correction cannot underflow and panic the
  coordinator. The test at `heartbeat.rs:1174` covers the backward direction.
- **A stale entry is not destroyed** — `effective()` does not mutate, so a
  returning heartbeat recovers on its next insert.
- **The turn heartbeat never goes stale** — it ticks and sends
  `beating: false` when unarmed rather than going quiet.

**Half-open, deliberately not filed:** the correctness bug is fixed but the map
still never *evicts*. Growth is bounded by the number of distinct heartbeat
labels a guest sees — a handful in an ephemeral VM — so this is a memory note,
not a leak worth a card.

**Nit:** the worst-case timing test (`heartbeat.rs:1160`) uses `2 * INTERVAL - 1`
rather than the exact worst case, stopping one tick short of the real boundary.
