## What to build

Carry a card in and out of the icebox through the one verb the owner already
knows: `project status set`. Add an `icebox` target token and teach `status set`
the three edges.

- **Promote out.** `project status set <id> todo` on an iced note adds a To-do
  card for it, at the front of the pipeline. A promotion targets To-do only
  unless `--force` (a promotion into another lane is the deliberate exception).
- **Shelve back.** `project status set <id> icebox` removes the card and keeps
  the note. `icebox` is a new target token. A shelve from To-do is clean; a
  shelve from an active lane (in-progress, needs-review, ready) needs `--force`.
- **Cancel from the icebox.** `project status set <id> cancelled` on an iced note
  stamps the note's `disposition`/`disposition_at` tombstone and adds a
  `- [x] [[<id>]]` line to `## Archive` — the same tombstone every cancelled card
  gets — without a stop in an active lane.

The decision (design pseudocode — shape, not implementation):

```
status_set(id, target, force):
    note = load_note(id); on_board = board_has_card(id)
    if target == icebox:                 # shelve
        if not on_board: return           # already iced, no-op
        if lane_of(id) != todo and not force: reject
        board_remove_card(id); return
    if not on_board:                      # promote / cancel out of icebox
        if target == cancelled:
            stamp_disposition(note, cancelled); board_add_archived(id); return
        if target != todo and not force: reject
        board_add_card(id, lane=target); return
    enforce_existing_transition(id, target, force)   # already on the board
```

### Seam (verified against the tree)

- The target is `to: Status` today (`set_status::apply`, `set_status.rs:90`).
  `icebox` is not a `Status`. Introduce a target type (e.g. an enum
  `Status | Icebox`) at the CLI/`set` boundary (`StatusArg` for `set` in
  `main.rs:140-160`, routed via `mod.rs:80-104`), or branch before `apply`.
- Reuse existing board primitives: promote = `insert_card(Status::Todo,...)`;
  shelve = `remove_card`; cancel-from-icebox tombstone can be done with
  `insert_card(Todo)` then `move_card(Cancelled)` (which ticks `- [x]` and pushes
  to `## Archive`) — no new board API needed — plus the disposition stamp via
  `update_note` (`set_status.rs:169-192`). Confirm this matches `move_card`
  behavior (`board.rs:304-324`).
- When the card is already on the board, keep the existing transition gate
  (`transition_allowed`, `state.rs:24-39`) unchanged.
- Order the two halves of cancel-from-icebox so a partial run leaves the card
  promotable and repeatable, never half-tombstoned.

## Acceptance criteria

- [ ] `status set <id> todo` on an iced note adds a front-of-To-do card;
      a non-todo promotion target without `--force` is rejected.
- [ ] `status set <id> icebox` on a To-do card removes it and keeps the note;
      shelving from an active lane without `--force` is rejected.
- [ ] `status set <id> cancelled` on an iced note stamps the tombstone and adds
      the `- [x]` archive line, with no active-lane stop.
- [ ] `status set <id> icebox` on an already-iced note is a no-op.
- [ ] Unit tests, BDD-named: `it_promotes_an_iced_note_into_todo`,
      `it_rejects_a_promotion_to_a_non_todo_lane_without_force`,
      `it_shelves_a_todo_card_back_to_the_icebox`,
      `it_rejects_a_shelve_from_an_active_lane_without_force`,
      `it_cancels_an_iced_note_straight_into_the_archive`.
