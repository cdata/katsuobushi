## What to fix

`sandbox fetch` silently destroys landed work when a card goes through more than
one review turn. Two incidents in a single `implement` session; the second
abandoned **5 commits** and wiped the tests of **two unrelated cards** that had
already reached `ready`.

### The mechanism

The two documented workflows contradict each other once a review bounces.

1. The **landing** procedure (sandbox skill, "Change integration") says to
   `sandbox fetch`, then **rebase** the guest's commits onto the current tip of
   your work. In a colocated jj repo, rebasing moves the `sandbox/<name>`
   bookmark to the host's *rebased copy*.
2. The guest's mirror is frozen at its launch and its local branch still points
   at the **original** commit. On a bounce it pushes its next commit onto that
   original.
3. The next `sandbox fetch` force-updates `refs/heads/sandbox/<name>` away from
   the host's rebased copy. jj now sees that copy as unreachable, **abandons**
   it, and rebases its descendants — which are the host's own later commits.

The host's landed content vanishes. Anything committed on top of it — including
other cards landed in the meantime — is rebased onto a base that no longer
contains it.

### Why the docs do not warn you

The skill states:

> The fetch force-updates the local `sandbox/<name>` branch to the guest's tip.
> The leading `+` (force) is what makes it idempotent: refetching an instance
> you already landed once — every review bounce — updates the branch instead of
> failing non-fast-forward.

That is true of the **ref** and false of the **repository**. The force-update is
idempotent only if nothing was built on the old ref — but the landing procedure
one section earlier instructs you to build on it. "Every review bounce" is named
as the supported case, and it is exactly the case that breaks.

### Why it is dangerous rather than merely annoying

The failure is silent and reads as housekeeping. jj prints:

```
Abandoned 5 commits that are no longer reachable.
Rebased 3 descendant commits off of commits rewritten from git
```

Nothing says content was lost. A `jj log` afterwards looks entirely plausible —
the commits that remain have sensible messages and a sensible shape. In both
incidents the loss was found only by grepping the working copy for **content**
that should have been there (`resolve_rush`, `it_registers_drive_card_tells`,
`falling-edge`), never by reading history.

The blast radius is also not confined to the card being fetched. The second
incident destroyed the tests from cards `60d871` and `05e675`, which had nothing
to do with the fetch — they were simply descendants.

### Recovery, for whoever hits this before it is fixed

`jj op restore <op-before-the-git-import>` recovers everything; the operation to
target is the one immediately preceding `import git refs`. Do **not** try to
repair it commit by commit: rebasing the individual guest commits makes it
worse, because their diffs are computed against their original parents and
revert each other.

To land a follow-up commit safely afterwards, take its content rather than its
commit:

```sh
jj restore --from <guest-commit> <paths>
```

That never moves the bookmark and never orphans anything.

## Options

Left open; more than one may be worth taking.

- **Fetch into a non-moving ref.** Give each fetch its own ref
  (`refs/sandbox-fetch/<name>/<seq>`, or keep `sandbox/<name>` but never
  force-move it once the host has descendants). The host's landed copy is then
  never orphaned, and the "idempotent refetch" property becomes true of the
  repository and not just the ref.
- **Warn before orphaning.** `sandbox fetch` can see that the current
  `sandbox/<name>` has local descendants that the incoming tip does not contain,
  and refuse or warn rather than force-updating into a silent abandon.
- **Document the multi-turn landing path.** The skill's landing procedure covers
  the first fetch well. It needs a second paragraph for the bounce case, saying
  plainly that rebasing a follow-up guest commit onto work you already landed
  will orphan it, and that `jj restore --from` (or `git cherry-pick`) is the
  supported move.
- **Have the host land off the bookmark.** If the landing procedure moved the
  guest's commits onto a host-owned name and left `sandbox/<name>` pointing only
  ever at guest history, the force-update would have nothing of the host's to
  orphan.

### Seam

## Host investigation — mechanism confirmed by reproduction

A minimal reproduction (scratch repo, colocated jj, no sandbox required)
reproduces the production symptom **exactly**, including the messages:

```
Abandoned 2 commits that are no longer reachable.
Rebased 1 descendant commits off of commits rewritten from git
```

Sequence: host has a board commit → fetches guest commit A → **rebases A onto the
board commit** (the landing procedure) → adds work on top → the guest, whose
mirror is frozen at A's parent, pushes B onto the **original** A → host fetches
again. The board commit is abandoned and its file disappears from the working
copy.

**The trigger is the host rewriting a commit that the incoming ref still points
at.** `refs/heads/sandbox/<inst>` is imported by jj as a **local** bookmark. When
the force-update moves that local bookmark back onto the original commit, jj
reads the host's rebased copy as *rewritten from git*, abandons it, and rebases
its descendants — which is where board commits are lost.

Changing only the refspec destination to `refs/remotes/…` and repeating the
identical sequence produces **no abandon, no rewrite, and the board commit
survives**. jj imports `refs/remotes/*` as a *remote* bookmark, and a remote
bookmark moving is not a rewrite of local history.

Two caveats worth carrying into the fix, both observed:

1. An untracked remote bookmark is **immutable** under jj's default
   `immutable_heads()`, so `jj rebase` on it is refused unless the consumer
   overrides that. This structurally prevents the orphaning — but it also means
   the current landing procedure ("rebase the sandbox commits onto your tip")
   stops working as written.
2. `jj rebase -r <name>@<remote>` does not move the remote bookmark, so the
   rebased result is an anonymous head. The landing procedure needs to name what
   the host lands *onto* rather than relying on the bookmark following.

Reproduction script kept at `scratchpad/repro.sh` (takes `heads` or `remotes`);
it should become the regression test the fourth acceptance criterion asks for.

**Also confirmed:** the fix is not only a refspec change. The orphaning requires
the host to rewrite the guest commit. A landing procedure that never rewrites
guest history — rebasing the host's own commits **onto** the guest's instead —
made every subsequent import a no-op in practice during the PDD003 session, until
two concurrent branches had to be linearised, which forced a rewrite again.

## Settled design (owner decision: change both the refspec and the landing)

The orphaning needs **two** ingredients: a jj-**local** bookmark, and the host
**rewriting** the commit that bookmark still points at. Remove both.

### 1. The guest ref becomes a remote bookmark

`sandbox fetch` writes `+sandbox/<inst>:refs/remotes/<remote>/<inst>` instead of
`refs/heads/sandbox/<inst>`. jj still imports it (it reads `refs/heads/*`,
`refs/tags/*` **and** `refs/remotes/*`), so the 0.4.0 invisibility bug that
`02e25f4c` fixed does not come back. But a remote bookmark moving is not a
rewrite of local history, so the force-update has nothing to abandon.

Verified: identical bounce sequence, only the refspec differing —
`refs/heads/` abandons the host's board commit, `refs/remotes/` does not.

### 2. The host lands by duplicating, never by rebasing

`sandbox/<inst>` points at **pure guest history, forever**. The host never
rewrites it. Landing is `jj duplicate <guest revs> -d <host tip>` (git:
`cherry-pick`), which copies the guest's work onto host history and leaves the
guest ref untouched.

These two changes **reinforce** each other rather than conflict. An untracked
remote bookmark is immutable under jj's default `immutable_heads()`, so `jj
rebase` on it is *refused* — the tooling now structurally enforces the landing
rule instead of relying on an orchestrator remembering it. Verified that
`jj duplicate` of such an immutable commit **is** permitted, so the landing path
works under the default with no consumer config.

### 3. The fetch guard stays, as defence in depth

Even with both changes, `sandbox fetch` should detect that an incoming tip would
orphan local descendants and refuse rather than proceed. It is the safety net for
a landing that went off-script, and it is what turns a future regression into a
loud failure instead of silent data loss.

### Consequences for the sibling cards

This landing contract is the spine the other two hang off:

- **`9344ec`** (attribution, descriptions, vestigial lineages) — the duplicate
  step is the natural seam for attribution. A duplicated commit is created by the
  host, so the host can set the author to the repository owner there, which
  settles that card's open design question without giving the guest the owner's
  identity.
- **`c72eb6`** (prune refs and mirrors at acceptance) — becomes simple. Once
  `sandbox/<inst>` only ever holds guest history with no host descendants,
  deleting it at acceptance cannot strand host work. That card was iced pending a
  design; this is the design it was waiting for.

### Not yet settled — decide during implementation

- Which remote name to use, and whether to create a real git remote per instance
  or write the ref directly. Writing directly is simpler; a named remote may read
  better in `jj log`.
- Whether landing should duplicate the whole guest branch each time, or only the
  commits not yet landed. The bounce case makes this a real question: after
  landing A, a bounce pushes A+B, and only B is new.
- Whether to keep a host-owned bookmark naming the landed copies, so the revert
  artefact is still findable after the guest ref is pruned.

### Reproduction

Self-contained; needs no sandbox. Run as `bash repro.sh heads` (reproduces the
failure) and `bash repro.sh remotes` (demonstrates the fix). This should become
the regression test the fourth acceptance criterion asks for.

```bash
#!/usr/bin/env bash
# Reproduce the sandbox-fetch orphaning bug, then test the refs/remotes/ hypothesis.
#
# Mirrors a real review bounce:
#   host has a board commit; fetches guest-A; REBASES it onto the board commit
#   (the skill's landing procedure); adds a working commit; then the guest —
#   whose mirror is frozen at guest-A's parent — pushes guest-B onto the
#   ORIGINAL guest-A, and the host fetches again.
set -u
DEST_REF="$1"
ROOT=$(mktemp -d); cd "$ROOT" || exit 1

git init -q --bare mirror.git
git init -q seed && cd seed
git -c user.email=s@x -c user.name=s commit -q --allow-empty -m "base"
git push -q ../mirror.git HEAD:refs/heads/main
git -c user.email=g@x -c user.name=g commit -q --allow-empty -m "guest-A"
git push -q ../mirror.git HEAD:refs/heads/sandbox/card-x
cd ..

# Host repo: init + fetch main only, so the sandbox branch is NOT a remote
# bookmark (matching the real repo, where fetch writes the ref directly).
git clone -q mirror.git host && cd host || exit 1
git remote remove origin          # no remote bookmarks: matches the real repo
git checkout -q main 2>/dev/null || git checkout -q -B main
jj git init --colocate >/dev/null 2>&1
printf '[revset-aliases]\n"immutable_heads()" = "none()"\n' >> .jj/repo/config.toml

# Host's own board commit, on top of main.
jj new main >/dev/null 2>&1; echo board > BOARD.md
jj describe -m "chore-board" >/dev/null 2>&1
BOARD=$(jj log -r '@' --no-pager --no-graph -T 'change_id.short()')

if [ "$DEST_REF" = heads ]; then
  SPEC="+sandbox/card-x:refs/heads/sandbox/card-x"; REV='sandbox/card-x'
else
  SPEC="+sandbox/card-x:refs/remotes/sbx/card-x";    REV='card-x@sbx'
fi
echo "### refspec: $SPEC"
git fetch -q ../mirror.git "$SPEC"; jj st >/dev/null 2>&1

echo "### host rebases the guest commit onto its board commit (the landing step)"
jj rebase -r "$REV" -d "$BOARD" 2>&1 | tail -1
jj new "$REV" >/dev/null 2>&1
jj describe -m "host-work-on-top" >/dev/null 2>&1
TOP=$(jj log -r '@' --no-pager --no-graph -T 'change_id.short()')

# Guest's frozen mirror pushes the bounce commit onto the ORIGINAL guest-A.
cd ../seed
git -c user.email=g@x -c user.name=g commit -q --allow-empty -m "guest-B-bounce"
git push -q -f ../mirror.git HEAD:refs/heads/sandbox/card-x
cd ../host

echo "### second fetch (the bounce):"
git fetch -q ../mirror.git "$SPEC"
jj st 2>&1 | grep -iE "abandon|rewritten|conflict" || echo "  (no abandon/rewrite/conflict reported)"

echo -n "### board commit ($BOARD): "
jj log -r "$BOARD" --no-pager --no-graph -T 'description.first_line()++"\n"' 2>/dev/null | grep -q chore-board && echo SURVIVED || echo GONE
echo -n "### host work commit ($TOP): "
jj log -r "$TOP" --no-pager --no-graph -T 'description.first_line()++"\n"' 2>/dev/null | grep -q host-work && echo SURVIVED || echo GONE
echo "### final @ :"; jj log -r '@' --no-pager --no-graph -T 'change_id.short()++" "++description.first_line()++"\n"' 2>/dev/null
echo -n "### BOARD.md in working copy: "
[ -f BOARD.md ] && echo present || echo MISSING
cd /; rm -rf "$ROOT"
```

A second harness exercising the duplicate-based landing across a bounce was
drafted during planning; its revset for locating a duplicated commit was wrong
and it needs rewriting. Rebuild it as part of the work rather than trusting the
draft.

### BLOCKING defect found by running the shipped code

**The guard false-positives, and permanently blocks re-fetching any pre-existing
instance.** A second `sandbox fetch` of this very instance fails:

```
Error: refusing fetch: local branches refs/heads/sandbox/card-c1a6e1-b864eea9
descend from the current sandbox-guest/card-c1a6e1-b864eea9 tip …
```

Two distinct problems behind it:

1. **Migration debris is not handled.** Every instance fetched *before* this
   change still has a `refs/heads/sandbox/<inst>` ref. `--contains <tip>` matches
   a ref that **is** the tip (a commit contains itself), so the guard refuses.
   That ref is pure guest history and has nothing of the host's to orphan — it is
   exactly the case the guard should ignore. As shipped, every instance carried
   over from before the fix becomes un-refetchable.
2. **The error message's advice is circular.** It says to use
   `jj duplicate`/`git cherry-pick` "rather than re-fetching" — but re-fetching
   is how the new guest commits are *obtained*. You cannot duplicate commits you
   have not fetched. The guidance needs to tell the operator how to get unstuck,
   not to do the impossible.

## Review notes

### Round 1 — `review-c1a6e1-3eb9b335` — VERDICT: needs-changes

Gates: 462 rust tests pass, `rust lint` clean, `markdown lint` clean.

**The false positive is confirmed, with the exact mechanism:**

- First post-upgrade fetch: no `refs/remotes/sandbox-guest/<inst>` yet →
  `read_remote_ref_tip` returns `None` → guard skips → fetch succeeds and sets
  the new ref to `guest-tip-A`.
- **Second fetch:** tip is now `guest-tip-A` → `--contains=guest-tip-A refs/heads/`
  returns the leftover `refs/heads/sandbox/<inst>`, which points at *exactly*
  that commit → guard refuses.

So every pre-existing instance migrates on its first fetch and hits a wall on the
second. A hard block on all migrated instances.

**Recommended predicate — strict descent, not containment.** Add
`%(objectname)` to the `for-each-ref` format and filter out any entry whose
object *is* the old tip. Verified in a scratch repo: migration debris produces
zero results; a `main` carrying a real host commit on top of the guest commit is
still caught; and duplicate/cherry-pick landing leaves the guest SHA out of host
branches entirely.

**The guard is load-bearing — with the fix.** The refspec change alone fully
prevents the data loss, so the guard is a secondary net for an operator still
running the old rebase landing. That risk is real, but *as shipped* the guard
"blocks legitimate re-fetches more reliably than it catches bad rebases". With
strict descent it earns its complexity and should be kept.

**Further findings:**

1. **The error message is circular** (confirmed). Its secondary advice — "ensure
   no local branch descends from the old tip" — is actionable for the genuine
   bad-rebase case, but in the false-positive case the operator must delete
   `refs/heads/sandbox/<inst>` by hand, which the message never says.
2. **`git cherry-pick <name>@sandbox-guest` in SKILL.md is invalid git syntax.**
   `@sandbox-guest` is jj notation; `git rev-parse` rejects it. The correct git
   form is `git cherry-pick sandbox-guest/<name>`, which resolves via
   disambiguation even with no configured remote.
3. **The scoped "idempotent" claim is still wrong for migrated instances** —
   repository-level idempotency holds for new instances only, and the Bounce
   section does not mention the migration case at all.
4. **Consumer impact is unrecorded.** This is the **third** ref-namespace change
   in three releases (`refs/katsuobushi/` → `refs/heads/sandbox/` →
   `refs/remotes/sandbox-guest/`). `MIGRATING.md` 0.4.1 still tells consumers to
   read `sandbox/<inst>`; there is no `CHANGELOG.md` or `MIGRATING.md` entry for
   this change; and the old refs are left behind.
5. **The tests pass while the binary refuses a legitimate re-fetch.**
   `it_fetches_the_same_instance_twice_without_non_fast_forward` pre-loads
   `for-each-ref` with empty output, modelling the happy path but not the
   migration-debris path; and
   `it_refuses_when_a_local_branch_descends_from_the_current_tip` returns a
   refname with **no objectname**, so it cannot model strict-vs-containment at
   all.
