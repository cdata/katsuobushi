## What to fix

Raised by the independent reviewer of card `12bead` as a non-blocking finding
and accepted alongside it, so it is filed rather than bounced.

`12bead` added a landing guard to the `sandbox` skill that restores the board
after a squash merge:

```sh
git checkout HEAD -- project/kanban/ >/dev/null 2>&1 || true
```

The `|| true` is **load-bearing** and must not simply be deleted: `git checkout`
on a directory exits non-zero when any path under it is absent from HEAD — the
guest-added-file case — and suppressing that is what allows the following
cleanup loop to run.

The cost is that the same suppression swallows a checkout failure arising from
any *other* cause. The orchestrator would see a landing that appears to have
guarded the board when it did not. That sits awkwardly with `12bead`'s own
AC 3: "If a guest branch does touch the board, the landing says so rather than
merging it quietly."

## What to fix

Distinguish the expected non-zero exit (paths absent from HEAD) from an
unexpected failure, so the first stays quiet and the second is reported. For
example, check the specific condition rather than blanket-suppressing, or verify
after the fact that `git diff --cached -- project/kanban/` is empty and say so
loudly when it is not.

## Acceptance criteria

- [ ] An unexpected `git checkout` failure during the landing guard is surfaced, not swallowed
- [ ] The guest-added-file case still works without noise
- [ ] The landing procedure still satisfies `12bead`'s AC 3

## Review notes

Reviewed by `review-283f02-ce7daf59` against branch tip `b744340`.
**VERDICT: accept.**

The reviewer tested the recipe against a scratch git repo rather than reasoning
from the prose, covering `A` (guest-added), `M`, `D`, a rename (`R100`), and a
genuine working-tree checkout failure induced with `chmod 555`.

- **AC 1** — mostly satisfied. For the primary failure modes (disk-full,
  index-lock, anything preventing an index update) `M`/`D` residue remains and
  the guard fires correctly.
- **AC 2** — fully satisfied, verified empirically: `A` entries survive the
  checkout, are filtered by `grep -v '^A'`, leave the residue check empty, and
  are removed by the cleanup loop. No noise.
- **AC 3** — fully satisfied. `12bead`'s warning `printf` and its `while` /
  `git rm` loop are unchanged and still reachable past the new guard.
- **Renames** — correctly classified, and this resolves a question the
  orchestrator raised. An `R100` decomposes under `git checkout HEAD --`: the
  deleted side is restored out of the index, the new side remains as `A`. The
  guard therefore only ever sees `A`. Verified empirically.
- **Two-block consistency** — the new guard is byte-identical in the plain-git
  and jj-colocated blocks; the note about git HEAD tracking `@-` is accurate.

Non-blocking findings, recorded but not filed:

- `SKILL.md:421`/`472` — the guard detects failure by reading the **index**, but
  `git checkout` updates the index even when the working-tree write fails
  (EACCES). In that specific case the guard does not fire. The reviewer
  confirmed the landing outcome is still correct — the kanban changes are
  excluded because the index *was* updated — and that the prior `|| true` code
  had the same gap, so this is not a regression. Left unfiled on that basis.
- `exit 1` exits the shell session when the block is pasted into an
  **interactive terminal**; in a subshell (how an agent executes it) only the
  subshell dies. The error is printed to stderr first, so the operator sees the
  cause either way. Not a correctness defect, but a human pasting the recipe
  loses their terminal and no documentation says so. Filed separately.

Markdown gate clean. Nothing left running.
