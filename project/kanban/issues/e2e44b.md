## What happened

During the entire pre-boot provisioning phase of a launch — mirror clone,
nix-db snapshot, context staging, secret staging — both documented
diagnostics are structurally silent:

- `sandbox status` derives an instance's state solely from QMP socket
  liveness (`rust/katsuobushi-controller/src/sandbox/status.rs:499`:
  `running = host.qmp_alive(&sock)`), and the QMP socket only exists once
  QEMU is up. `instance.json` is written before the recipe runs
  (`start.rs:162`), so the instance *lists* — as **stopped**.
- `console.log` is only created at the very last recipe step, when the
  runner execs QEMU (`start.rs:951`: `{runner} > console.log 2>&1 &`).
  Everything before that produces no on-disk log at all.

The sandbox skill points at exactly these two sources for diagnosing a stuck
boot (`plugins/katsuobushi/skills/sandbox/SKILL.md:353` and `:375`). In the
2026-08 arcanabasis post-mortem, an 11-minute provisioning stall (the nix-db
backup livelock, filed separately) left the operator with `/proc` spelunking
as the only diagnostic — and contributed directly to a destructive
kill-the-step intervention.

Related silent failure: when the nix-db snapshot is missing, the guest
seeding service skips via `ConditionPathExists`
(`lib/sandbox/default.nix:1421`) or rolls back on a failed sanity check
(`default.nix:1401-1459`) — by design best-effort — and the guest boots
"healthy" with a system-only DB. Nothing tells the host the seed was skipped;
the first symptom is an agent that cannot run any gate.

## Suggested fix

Three coordinated visibility improvements:

1. **Log the whole recipe, not just the runner.** Redirect recipe output from
   the top (e.g. `exec > console.log 2>&1` as an early recipe line, or a
   sibling `provision.log`), so every provisioning step's start/finish is
   on disk the moment it happens. Steps should echo begin/end markers
   (`::: snapshotting host nix DB …` / `::: done (0.4s)`).
2. **A provisioning phase in `status`.** Drop a small phase marker (e.g.
   `phase` file in the state dir written per recipe stage, removed on runner
   exec) and have `summarize` render `provisioning (<last step>)` instead of
   `stopped` when it is present. The pre-boot window — exactly when an
   operator most wants diagnostics — then has a truthful state.
3. **Surface the seed outcome.** The `katsuobushi-nixdb` guest service
   already writes journal+console lines; additionally write its verdict
   (`seeded` / `skipped-no-snapshot` / `rolled-back`) to the 9p share, and
   render it in `sandbox status <inst>` detail — e.g.
   `store db:   system-only (host seed skipped)` — so an unseeded VM is
   visible before an agent burns a session discovering it.

## Acceptance criteria

- [ ] Pausing the recipe mid-provisioning (e.g. SIGSTOP the snapshot step)
      shows `provisioning` with the current step in `sandbox status`, and the
      log file already contains that step's begin marker.
- [ ] A launch whose snapshot is absent boots a guest whose `status` detail
      names the system-only DB state.
- [ ] `console.log` (or `provision.log`) covers the full recipe from its
      first line; the skill docs are updated to match.

## Review notes

**Peer review (independent agent), 2026-08-04 — blocking finding, fixed.**

The pre-boot `phase` marker was removed only on the success path. A launch that
aborted mid-provisioning (an unreadable secret exits 1; `set -e`/Ctrl-C can end
the recipe anywhere) left it behind, so `sandbox status` reported
`provisioning (<step>)` forever for an instance with no VM — strictly worse than
the `stopped` it reported before, and actively misleading to an orchestrator
that follows MIGRATING's guidance to treat `provisioning` as a live launch.

Fixed: the recipe arms `trap 'rm -f <phase>' EXIT INT TERM` before the first
phase; verified against the unreadable-secret repro. A comment claiming the
marker survives until QMP answers was also wrong and has been corrected. The
SIGKILL residual is filed separately.

Also fixed here: provisioning output was teed with `2>&1`, sending the recipe's
own failures to the caller's stdout; each stream is now teed to its own
descriptor.
