## What to build

`sandbox fetch`'s refusal message ends with guidance that can no longer fire.

Before strict descent, a listed ref might have been the migration debris — a
`refs/heads/sandbox/<inst>` pointing at exactly the guest tip — so telling the
operator "if its tip is pure guest history, delete it" was the right recovery.
The strict-descent fix filters that case out before the message is ever built.
Any ref that reaches the message now carries commits on top of the tip, so it is
never pure guest history.

The clause therefore contradicts the paragraph above it, which correctly says the
listed branches have commits on top. An operator reading both is told two
incompatible things about the same refs at the moment they are already stuck.

Delete the stale clause and leave the guidance that still applies: the listed
branches carry host work rebased onto the guest tip, and that work should be
cherry-picked to a new branch before re-fetching.

## Acceptance criteria

- [ ] The refusal message contains no advice that strict-descent filtering makes
      unreachable.
- [ ] The remaining guidance is correct for every ref that can actually be listed.
- [ ] A test pins the message's content so the two halves cannot drift apart again.

## Review notes

### Round 1 — `review-0ef455-e21284e8` — VERDICT: accept

Gates: 607 tests, `rust lint` clean, `markdown lint` clean.

**The unreachability premise holds — traced, not assumed.** The `filter_map` at
`fetch.rs:146-153` has three arms: a genuine descendant (`obj != old_tip`) is
kept, `obj == old_tip` is **dropped before the vec is built**, and an unparseable
line is kept conservatively. So no ref whose tip equals the current tip can reach
the `bail!` message. The deleted advice was genuinely unreachable.

**The surviving message gets an operator unstuck** — it names the listed refs,
explains the consequence, and prescribes the cherry-pick action. The reviewer
noted the "if any" qualifier is now technically redundant (every listed ref is a
genuine descendant by construction) but not misleading.

**The test is at the right granularity.** The positive assertion survives
innocuous rewording; the negative assertions pin the two removed phrases. They
would not catch a *creative* rewording of the stale clause, which the reviewer
judged an acceptable limit for negative assertions — their job is to catch
re-introduction of known-bad text.

Minor structural note, not actioned: the new test duplicates the scenario of
`it_refuses_when_a_local_branch_descends_from_the_current_tip` and could have
been extra assertions on that test instead.

No other stale guidance survives in the file from the containment-to-strict-descent
change.
