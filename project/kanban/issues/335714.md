## What to build

Card `9689a8` shipped a library heartbeat set and its peer review confirmed the
checks work when run by hand inside a VM. The review also recorded four smaller
defects around the wiring. None blocked that card. Together they are worth one
pass.

- **Silent absence.** When `KATSU_SHIPPED_HEARTBEATS` is unset the server skips
  the shipped directory with no log line and no error (`server.rs:1071-1073`). A
  deployed VM always has the variable, so the failure is invisible exactly where
  it is most confusing — a non-Nix development environment, where the protection
  the card exists to guarantee is simply absent and nothing says so.
- **A doc comment that is wrong.** `runner.rs:34` says `run_heartbeat_set`
  "Never returns normally". It spawns its tasks and returns; the *inner* tasks
  are the ones that never return.
- **Undefined-looking label collision.** A project heartbeat carrying the same
  label as a shipped one is not deduplicated. Both run and both appear in the
  work state. That follows from "a project directory adds to the shipped set, it
  never replaces it", so the behaviour is right — but it is neither documented
  nor tested, and a reader would reasonably expect the project file to win.
- **A latent Nix build failure.** The `*.yaml` glob at `default.nix:357` would
  fail the build if the shipped heartbeat directory ever became empty.

## Acceptance criteria

- [ ] A server started with `KATSU_SHIPPED_HEARTBEATS` unset says so on stderr,
      once, naming what is missing and what it means.
- [ ] `run_heartbeat_set`'s doc comment describes what the function actually
      does.
- [ ] The label-collision rule is stated where a heartbeat author will read it,
      and a test pins it.
- [ ] An empty shipped heartbeat directory does not fail the Nix build.
- [ ] A test covers an empty `hb_dirs`.
- [ ] `clippy -D warnings` is clean.

## Review notes

### Round 1 — `review-335714-1c438525` — VERDICT: needs-changes

Gates: 579 tests pass (459 + 64 + 46 + 10, matching the host), lint clean.

**BLOCKING — the label-collision rule does not reach an author.** It is
documented only in the `collect_heartbeats` Rust doc comment
(`runner.rs:37-41`). The sandbox skill's "Authoring heartbeats" section
(`SKILL.md:468-551`) says nothing about it. The criterion is explicit — *"stated
where a heartbeat author will read it"* — and an author writing
`.katsuobushi/heartbeats/` YAML reads the skill, not Rust internals. The
reviewer's point is sharper than mere placement: an author who gives a project
heartbeat the same label as a shipped one will likely expect **override**
semantics, since that is the common layered-config convention, and will instead
get both running with nothing to tell them otherwise.

**Everything else passed:**

- **The unset-variable message fires exactly once.** It sits at
  `server.rs:1347-1351` inside `main()`, ten lines *before* the
  `tokio::spawn(run_heartbeat_set(...))` at `:1358`, and the rescan loop lives
  entirely inside that function (`runner.rs:96-119`). Structurally unreachable
  on a rescan — the host's spam concern does not apply.
- **The message is useful** — it names the variable, states the consequence
  ("shipped heartbeats will not run") and gives the corrective action.
- **The Nix `find` fix is reproducible.** Each file is copied independently to a
  deterministic path, so traversal order has no effect on the output. Confirmed
  by building the derivation.
- **Both new tests are solid** —
  `it_keeps_both_heartbeats_when_labels_collide_across_directories` asserts both
  `len() == 2` **and** that two entries carry the shared label, so it genuinely
  proves both survive rather than asserting a length.

**Note on the doc-comment finding:** the reviewer judged the *old* wording
("Never returns normally") to have become accurate again, because `612108` gave
`run_heartbeat_set` its own `loop {}` — it is now the loop owner, not merely a
spawner. The original defect had gone stale between being filed and being fixed.
The new wording is still preferred as more informative.
