## What to build

Say **orchestrator-only** where the skills now say **host-only**.

The board is written by one role, not by one machine. That role runs on the host
today and does not have to. Naming the machine couples the rule to a deployment
detail, and a later design that moves the orchestrator into its own sandbox then
reads as a contradiction.

Known sites:

- `plugins/katsuobushi/skills/project-orchestration/SKILL.md` line 80 — the
  heading "The board is host-only (an invariant)".
- `plugins/katsuobushi/skills/sandbox/SKILL.md` line 307 — "`project/kanban/` …
  is host-only state, and the host is its single writer".
- `rust/katsuobushi-controller/src/sandbox/dispatch.rs` line 351 — the comment
  "The board is host-only (design/PDD001)".

Sweep for others rather than trusting this list.

This is a rename of the **role**, not of every mention of the host. Where the
prose genuinely means the machine — the host seam, the host repo, `HostImpl` —
leave it. The guest-facing rule is unchanged in substance: a guest never writes
the board.

## Acceptance criteria

- [ ] The skills say the board is orchestrator-only state and the orchestrator
      is its single writer
- [ ] No skill couples the board-writer role to the host machine
- [ ] The `dispatch.rs` comment matches the skills
- [ ] Mentions of the host that genuinely mean the machine are left alone
