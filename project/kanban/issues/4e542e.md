## What to build

`jj` is not available inside a sandbox guest. It is not in the guest's `packages`
list, and it is not supplied by the dev shell either — on the host it resolves to
the user's system profile (`/etc/profiles/per-user/<user>/bin/jj`). So a guest
that runs `nix develop` still has no `jj`.

That is a real hole for this project specifically. The landing story is
Jujutsu-shaped: the `sandbox fetch` refspec exists to be jj-visible, the orphaning
bug is a jj history-rewrite behaviour, and the landing procedure is written around
`jj duplicate`. None of it can be exercised by a peer reviewer in a sandbox.

It surfaced on card `c1a6e1`. The central claim — that moving the fetched ref to
`refs/remotes/` stops jj abandoning host commits — had to be verified by the
orchestrator on the host, because the reviewer had no `jj` to run the
reproduction with. An orchestrator verifying is weaker than an independent
reviewer verifying, and on a card about data loss that gap is worth closing.

Adding `jj` to the guest's `packages` is probably the whole fix. Check first
whether anything depends on its absence: the dispatch instructions tell agents to
use `git` and never `jj`, which is right for a guest working in a plain clone, and
that guidance should survive. The goal is that a reviewer can *test* jj behaviour
in a scratch repo, not that guest work switches VCS.

## Acceptance criteria

- [ ] `jj` is available on a guest's `PATH`.
- [ ] A guest can create a scratch colocated repo and run the `c1a6e1`
      reproduction to completion.
- [ ] The dispatch instructions still tell agents to use `git` for their own
      workspace, and say plainly why `jj` is present anyway.
- [ ] The sandbox skill notes that jj-dependent behaviour is now reviewable in a
      guest, so future cards do not repeat the workaround.
