## What to build

`jj metaedit --update-author` is the re-authoring mechanism card `9344ec`
documents in the sandbox skill. In this repository it does not work, and it fails
in the worst way: **it reports success.**

Observed repeatedly on jj 0.41.0:

```
$ jj metaedit --update-author -r 'nrurlyrr | tknuwtlw | ryvozwov'
Modified 3 commits:
  ryvozwov 5ac7f6b6 docs(orchestration): document fresh-reviewer protocol …
  tknuwtlw 62beedaa docs(orchestration): fix three contradictions …
  nrurlyrr ba807ff0 feat(sandbox): refuse dispatch when agent-authored commits …

$ jj log -r 'nrurlyrr | tknuwtlw | ryvozwov' -T 'commit_id.short() ++ author.email()'
9bf7545dae58  agent@katsuobushi.local
b8187322dcae  agent@katsuobushi.local
9f89191ca985  agent@katsuobushi.local
```

The commits are unchanged, the change ids still resolve to the **old** commit
ids, and `jj op log` records **no operation** for the metaedit — the most recent
operations are the preceding `jj new` / `jj duplicate`. Re-running produces a
different set of "new" commit ids each time, with the same non-effect.

Two things it is **not**. It is not an immutability refusal: an immutable target
produces a loud `Commit … is immutable` error, which was also observed and is a
different outcome. And it is not a bad invocation: `-r` is documented as an alias
for the positional `REVSETS` argument, and the command names exactly the intended
commits back.

It is also not uniformly broken — the same command re-authored at least one
landed commit earlier in the same session, verified by reading `author.email()`
afterwards. The condition that distinguishes the two cases is unknown and is the
thing to find.

Work out why, then fix the documented procedure. Possible directions, none
verified: an interaction with the colocated git repo's automatic export/import
cycle reverting the rewrite; a jj 0.41-specific defect; or something about
commits produced by `jj duplicate` specifically, since every failing case here
was a duplicate.

Until it is understood, `9344ec`'s procedure tells an orchestrator to run a
command that may silently do nothing.

## Correction — the root cause is immutability, not signing

The original report blamed commit signing. That was wrong, and the correction
matters because it changes what the fix has to address.

Signing **was** genuinely broken at the time — the key lives on a hardware token
and the agent socket was unreachable, so jj could not write a commit it wanted to
sign (a scratch repo could not even initialise: `Signing error`). That was real,
but it was a **separate** problem, and it resolved when the token became
reachable again.

The silent no-op has a different trigger. Verified afterwards, with signing fully
working:

- `jj metaedit --update-author -r <rev>` → prints `Modified 1 commits: <change>
  <new-id>`, changes nothing, records no operation.
- The same command with
  `--config 'revset-aliases."immutable_heads()"=none()'` → prints
  `Modified 1 commits` **and** `Rebased N descendant commits`, and the author
  actually changes.

So the determining factor is whether the target is **immutable**. And the real
defect is the **inconsistency**: an immutable target sometimes produces a loud
`Commit … is immutable` error — observed several times — and sometimes silently
reports success and does nothing. Same command, same repository, different
outcomes.

The presence of `Rebased N descendant commits` in the output is a reliable tell
that the rewrite actually happened. Its absence is the tell that it did not.

This matters for this project specifically because `c1a6e1` made guest refs
remote bookmarks, and jj's builtin `immutable_heads()` covers untracked remote
bookmarks — so **every commit becomes immutable as soon as the next card is
dispatched**. That is the normal state here, not an edge case.

Working recipe, verified end to end on 76 commits:

```
jj --config 'revset-aliases."immutable_heads()"=none()' metaedit --update-author -r <revs>
jj --config 'revset-aliases."immutable_heads()"=none()' sign -r <revs>
```

Revised acceptance criteria to fold in:

- [ ] Determine why an immutable target sometimes errors loudly and sometimes
      silently no-ops, and report it upstream if it is a jj defect.
- [ ] The landing procedure verifies the author after re-authoring rather than
      trusting the command's own success report.

## Scope note after PDD004

`PDD004` removes this bug from the critical path. Landing becomes a squash-merge
that creates a commit, so the routine workflow never rewrites a published commit
and never runs `jj metaedit`.

This card is **not** obviated, for two reasons:

- The behaviour is not specific to `metaedit`. Any jj command that rewrites a
  commit can meet an immutable target, and the inconsistency is the defect: the
  same situation sometimes produces a loud `Commit … is immutable` error and
  sometimes reports success and does nothing.
- Repairs still happen. Re-authoring and signing 76 commits in one session was
  such a repair, and it needed the override to work at all.

What changes is the priority. This was blocking an everyday procedure. It is now
a tool hazard worth knowing and worth reporting upstream.

Carried here from the cancelled `186265`: `jj metaedit`, `jj sign` and
`jj describe` all accept `--ignore-immutable`. Prefer that flag over a
`revset-aliases."immutable_heads()"` override wherever a rewrite is still needed.
