## What's wrong

0.4.0 changed `sandbox fetch` to land a guest branch in a per-instance tracking
ref:

```
refs/katsuobushi/<instance>
```

instead of the previous local branch `refs/heads/sandbox/<instance>`. MIGRATING
frames this as a pure improvement — a repeated fetch of an already-landed
instance no longer fails non-fast-forward — and for a Git consumer it is.

**For a Jujutsu consumer it is a regression: jj cannot see the fetched work at
all.** jj imports `refs/heads/*`, `refs/tags/*` and `refs/remotes/*`. It does not
import `refs/katsuobushi/*`, so the commits are in the object database but
unreachable from every revset:

```
$ jj log -r 'refs/katsuobushi/card-62c297-3ac37910'
Error: Revision `refs/katsuobushi/card-62c297-3ac37910` doesn't exist

$ jj log -r 'e72abdb2'            # the commit id the ref points at
Error: Revision `e72abdb2` doesn't exist

$ jj git import
Nothing changed.
```

`git for-each-ref` shows the ref perfectly. `jj git import` is a no-op because
there is nothing in an imported namespace to import.

## Why this matters more than it looks

**`sandbox fetch`'s success message names a ref that no longer exists**, which is
what sent me looking in the wrong place first:

```
fetched sandbox/card-62c297-3ac37910
```

There is no `sandbox/card-62c297-3ac37910`. The ref written was
`refs/katsuobushi/card-62c297-3ac37910`. On a repo that has fetched instances
under both layouts — i.e. any repo that upgraded mid-run — the old name usually
*does* still resolve, to a **stale** branch from before the upgrade. So the
message points at real-but-wrong commits rather than at nothing.

## The workaround

Bridge the ref into a namespace jj imports:

```sh
git branch -f sandbox/<instance> refs/katsuobushi/<instance>
jj git import
```

This works, but it re-creates by hand exactly the layout 0.4.0 removed, and it
has to run after every fetch.

## Suggested fixes, most → least preferred

1. **Write both refs**, or make the target namespace configurable. The
   non-fast-forward fix comes from never rebasing the tracking ref, not from its
   location — `refs/heads/sandbox/<inst>` would be equally safe if it is only ever
   force-updated to the fetched tip.
2. **Detect a colocated jj repo** (`.jj` beside `.git`) and additionally write or
   import a jj-visible ref.
3. **At minimum, fix the message and document the workaround.** Print the ref
   actually written, and put the `git branch -f` + `jj git import` recipe in
   MIGRATING's 0.4.0 section. Today a jj user is told the fetch succeeded and then
   cannot find the work.

## Watch for

- The old `refs/heads/sandbox/*` branches from before an upgrade are left in
  place, which is correct — they are the revert artifact — but it means the
  ambiguity above is the normal state of an upgraded repo, not an edge case.
- Whatever the fix, `sandbox fetch` must stay idempotent. That property is the
  reason for the change and is worth keeping.

## Acceptance criteria

- [ ] After `sandbox fetch`, the fetched tip is reachable from a jj revset in a
      colocated repo without a manual `git branch`
- [ ] A repeated fetch of an already-landed instance still does not fail
- [ ] `sandbox fetch` reports the ref it actually wrote
- [ ] The jj consequence is documented in MIGRATING's 0.4.0 section
