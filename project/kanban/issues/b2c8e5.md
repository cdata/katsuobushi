## What to build

The gating experiment from `design/warm-artifacts.md` §10 + §13.1. Everything in
F1 rests on an assumption nobody has measured: that cargo accepts a crane deps
bundle's fingerprints when the bundle is untarred into an interactive
`CARGO_TARGET_DIR` rather than inherited inside a derivation.

Run it in **two arms**, because they fail differently:

1. **Plain dev shell.** Untar a `depsFor { profile = "dev"; }` bundle into a
   scratch target dir, `export CARGO_TARGET_DIR` at it, `cargo check` the
   workspace, and record the first crate that compiles.
2. **Dev shell + crane's vendored source replacement.** Same, but with
   `CARGO_HOME` / `.cargo/config.toml` pointed at the vendor store path the
   bundle was built from.

Read the result: a workspace crate compiling first is a pass; `Compiling <some
third-party crate>` is a fail. Arm 1 failing while arm 2 passes means F1 needs
the vendor config, which is a small addition. **Both** arms failing is the
result that reshapes the proposal, and F1 should not be written until this
card reports.

Record `RUSTFLAGS`, rustc version, profile, and the two target-dir paths for
each arm — that data is the input to the F1a manifest design.

## Dispatch log

**2026-08-05, run on the host (no VM — owner chose host-side work this
session).** Three arms against the real `katsuobushi-workspace-deps-deps` bundle
(release, `target.tar.zst`, 76 MB), extracted with crane's own
`inheritCargoArtifacts` from
`/nix/store/i9lc…-inheritCargoArtifactsHook.sh`. Script kept at
`scratchpad/warm-exp.sh`; logs beside it.

| Arm                                        | first units re-run                          | Compiling / Checking | wall      |
| ------------------------------------------- | -------------------------------------------- | -------------------- | --------- |
| 0 — cold, empty target dir                  | proc-macro2, quote, unicode-ident            | 41 / 47              | 19.3 s    |
| 1 — seeded, default `CARGO_HOME`            | pin-project-lite, cfg-if, futures-core       | 41 / 47              | 19.5 s    |
| 2 — seeded + crane vendor source-replacement | katsuobushi-sandbox-protocol (workspace)     | 0 / 0 third-party    | **1.1 s** |

Controls: both seeded arms received identical trees (1408 files, 154 `.rmeta`,
~294 MB, same `decompressing …` line), so arm 1 is not a failed extraction —
cargo got the artifacts and threw them away.

Environment (input to the F1a manifest): rustc/cargo 1.96.0 on both sides;
`RUSTFLAGS` unset in the deps derivation **and** in the dev shell; no `.cargo/`
in this repo, so no config divergence; profile release on both sides (the bundle
runs `cargoWithProfile check --locked` + `build --locked`, so check units are in
it); target dirs differ by construction (store-built vs
`$XDG_CACHE_HOME/cargo-target/…`) and that did **not** prevent reuse in arm 2.

**VERDICT: F1 + vendor config.** Seeding a target dir alone is a no-op — the
proposal's §10 reasoning that `PackageId`/`SourceId` preservation makes the
source-path divergence harmless is refuted. Reuse requires the dev shell to
resolve dependencies through the *same* vendored source replacement the bundle
was built against.

Consequences recorded in `design/warm-artifacts.md` §10.1-10.2, and b1962a's body
updated: installing that config without hijacking the user's `CARGO_HOME` is now
an open design question, `KATSUOBUSHI_NO_SEED=1` must drop the vendor config too,
and the F1a manifest needs a vendor-dir field.

Caveat: 17× on a small workspace (19.3 s → 1.1 s). The mechanism transfers; the
15-25 minute saving this is meant to deliver is not measured here.

## Review notes

**Peer review 2026-08-05 — ACCEPT**, with one correction to this log's own
claims. The verdict (seeding alone is a no-op; the vendored source replacement
is the load-bearing variable) survived an adversarial re-run and is now properly
controlled. But the three arms recorded above did **not** isolate the cause: arm
2 changed two variables at once relative to arm 1 — it added the vendor config
*and* swapped `CARGO_HOME` wholesale. The reviewer ran the missing controls
(`scratchpad/warm-exp2.sh`):

- arm 3 — seeded + fresh `CARGO_HOME` with an *empty* config → 21.7 s, 41
  Compiling. A fresh `CARGO_HOME` buys nothing; the vendor config is decisive.
- arm 4 — *unseeded* + vendor `CARGO_HOME` → 19.9 s, 41 Compiling. Arm 2's speed
  is real artifact reuse, not the config alone.
- arm 5 — reproduction of arm 2 → 1.19 s, 0 Compiling, 3 workspace crates, rc 0.

Also: the "identical file counts" control cited above is weak as stated — arm 1
recompiled into the same filenames, so equal counts were guaranteed either way.
What actually rules out the alternatives is that the `.rmeta` **filenames are
byte-for-byte identical** across both seeded arms (e.g.
`libanstream-c0a0c859068d9221.rmeta`), i.e. cargo computed the same metadata
hash on both sides — so profile, RUSTFLAGS and rustc identity are all excluded,
leaving the fingerprint's source path. No global `~/.cargo/config.toml` exists
on this host to shadow arm 1.
