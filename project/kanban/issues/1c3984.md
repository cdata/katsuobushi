## What happened

`sandbox dispatch` claims the card (`todo → in-progress`), composes the
directive (`[.dispatch-instructions.md] + card title + body`), and hands off
to the agent-start path (`rust/katsuobushi-controller/src/sandbox/dispatch.rs:49-57`).
The launch recipe boots QEMU **detached** (`start.rs:951`) and then delivers
the directive by tail-calling `exec katsuctl … prompt "<directive>"` from
the same foreground process (`start.rs:853-889`). The directive text exists
only in that process's argv and the transient recipe — it is never written
to the instance state dir.

Consequence (2026-08 post-mortem, item 3): the operator killed the dispatch
process (collateral of killing a provisioning step that looked hung). The
detached VM came up healthy and idle; the board said `in-progress`; and the
directive was nowhere on disk. Recovery required hand-recomposing the
directive from the card + instructions file and delivering it with
`sandbox prompt` — error-prone, and only possible because the operator knew
the composition rule.

## Suggested fix

Persist the composed directive at launch and add a redelivery path:

- In the start path (beside the `instance.json` write, `start.rs:162`),
  write the full composed directive to `<stateGlob>/<inst>/directive.md`
  whenever a launch carries a `--prompt`. Directives are card bodies plus
  the project's instructions prelude — already plaintext on disk in the
  board — so persistence adds no secret exposure (secrets ride fw_cfg,
  never directives).
- Add `sandbox prompt <inst> --redeliver` (or `--from-file <path>`): read
  the persisted directive and deliver it as a fresh turn (fresh turn id from
  the liveness counter, normal delivery-ack semantics). This is exactly the
  manual recovery, made mechanical.
- Have the "prompt it with: …" hint that a promptless start prints
  (`start.rs:889`) — and the orchestration skill's recovery guidance —
  mention `--redeliver` when a directive file is present.

## Acceptance criteria

- [ ] After `sandbox dispatch <card>` is killed post-launch, the instance
      state dir contains the exact composed directive.
- [ ] `sandbox prompt <inst> --redeliver` delivers it verbatim as a new
      turn; a missing directive file fails with a clear message.
- [ ] An ephemeral instance's directive file is reaped with the rest of its
      state dir; a named instance's persists across stop/start.
- [ ] Skill docs (sandbox + project-orchestration) document the recovery.

## Review notes

**Peer review (independent agent), 2026-08-04 — accepted with a test improved.**

AC 3 (reap semantics) was "tested" by a test that deleted the state dir itself
and asserted the file was gone — a tautology that said nothing about
`stop --remove`. Replaced with the containment assertion the reap claim actually
rests on: the directive lives directly inside the per-instance dir that
`stop --remove` deletes.

The directive lives in the guest-writable share, so a guest can rewrite what
`--redeliver` sends; filed as its own card.
