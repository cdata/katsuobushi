## What to build

Say that the dispatch guard is a backstop.

Card `e7fd2b` added a guard that refuses a dispatch when agent-authored commits
would freeze. It exists because the old landing copied a guest commit and
repaired the author afterwards, and the next dispatch made that commit an
ancestor of a remote bookmark, after which the repair was refused. The guard
caught the routine case.

Once a landed commit is created by the owner (card `7f46b9`), there is no
routine case left. The guard keeps its value: it still catches work landed by
any other route. Its purpose changes from routine to backstop, and the code and
the skills should say so — otherwise a later reader deletes it as dead code, or
a reader who trips it looks for a re-authoring step that no longer exists.

Two things to do:

- Update the guard's comments and its refusal message so they describe what it
  now covers, and do not point at a procedure that has been removed.
- Update the skills that describe the guard for the same reason. Check the same
  places for the retired "re-author before the next dispatch" deadline and
  remove what is left of it.

Do **not** remove the guard.

## Acceptance criteria

- [ ] The guard is retained, and a comment says what it still covers and why it
      is no longer a routine catch
- [ ] The refusal message names a recovery an operator can still perform, and
      names no procedure that has been removed
- [ ] No skill or code comment still states that re-attribution must happen
      before the next dispatch
- [ ] Existing tests for the guard still pass, and any test name or comment that
      describes it as the routine path is corrected
