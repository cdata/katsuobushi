## What to build

Document how a reviewer gets the branch it reviews.

A branch is the unit under review. It is the review artifact and the revert
artifact, it carries the writer's name, and it keeps that name. The reviewer
reads **that branch**, not the owner's integrated tip — because nothing of the
card is in the owner's history until the review passes.

A guest sees exactly one host directory, so a reviewer cannot fetch from the
party that wrote the change. The orchestrator moves the branch into the
reviewer's mirror with the delivery verb from card `69d1df`, and the reviewer
fetches it there.

Write the peer-review protocol in
`plugins/katsuobushi/skills/project-orchestration/SKILL.md` to say:

- Which command the orchestrator runs, and when in the loop it runs.
- What the reviewer does in its own clone to read the branch, and how it names
  the branch tip.
- That a review round **adds** commits to the branch and never rewrites it, so
  the reviewer can answer "what changed since I last read this" with a range.
- What a re-review of a bounced card needs: the orchestrator delivers the
  updated branch again before the reviewer reads it.

This replaces the raw `git push` into another instance's storage that the
orchestrator has been doing by hand.

## Acceptance criteria

- [ ] The reviewer's workspace holds the branch under review, and the reviewer
      can name the branch tip and read its commits
- [ ] The orchestrator gives a reviewer the branch with one documented command
      and no raw `git push`
- [ ] The skill states that a review round adds commits and never rewrites the
      branch
- [ ] The skill gives the range a reviewer uses to read only what changed since
      the previous round
- [ ] The re-review path after a bounce is documented
