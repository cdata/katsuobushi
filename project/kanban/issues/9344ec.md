## What to build

Reading `jj log` after a swarm session shows three kinds of debris. Each is
individually small and together they make the history hard to read and hard to
trust.

- **Commits are not attributed to the owner.** Every commit a sandbox produces is
  authored `agent@katsuobushi.local`. The work is the owner's, landed in the
  owner's repository, and should be attributed to them. Signing may not be
  available in the guest, and that is acceptable — attribution is the requirement
  here, not a signature.
- **Commits with no description survive.** The landing procedure leaves
  working-copy commits with `(no description set)`. In a long session there were
  many. A commit with no message is not reviewable and not bisectable.
- **Vestigial lineages remain after the work is done.** Two sources. `sandbox
  dispatch` seeds a guest from `git stash create`, so each dispatch leaves
  `WIP on (no branch): …` and `index on (no branch): …` commits behind in the
  host repo. Separately, a bounced card's superseded guest commits stay reachable
  from the `sandbox/<inst>` bookmark after the work has landed and the card has
  been accepted.

The first two are host-side landing hygiene. The third overlaps with the existing
card on pruning sandbox refs and mirrors when work is accepted, and with the
`sandbox fetch` orphaning bug — decide whether to fold them together or keep them
separate once that bug's fix is settled.

Attribution is the one with a real design question behind it. The guest commits as
its own identity today, and the host knows whose repository it is. Settle whether
the guest should be given the owner's identity at launch, or whether the host
should re-author on landing, and say which and why.

## Acceptance criteria

- [ ] A commit produced by a sandbox and landed by the host is attributed to the
      repository owner, not to an agent identity.
- [ ] The chosen mechanism (guest identity at launch vs. host re-author on
      landing) is written down with its reason.
- [ ] Landing a branch leaves no commit with an empty description.
- [ ] A dispatch leaves no `WIP on (no branch)` or `index on (no branch)` commit
      behind in the host repo once its card is accepted.
- [ ] Superseded guest commits from a bounced card are not reachable once the
      card is accepted.
- [ ] The landing procedure in the sandbox skill states these as requirements, so
      an orchestrator follows them by default rather than tidying afterwards.


## Design note (from the `c1a6e1` planning pass)

`c1a6e1` settles a landing contract that answers this card's open question about
attribution. Under it the host stops rebasing guest commits and instead
**duplicates** them onto host history (`jj duplicate` / `git cherry-pick`).

That duplicate step is the seam. The copy is created **by the host**, in the
owner's repository, so the host sets the author there. The guest keeps its own
identity in its own branch — which is honest about who ran the command — while
everything that lands in the owner's history is attributed to the owner. That is
strictly better than handing the guest the owner's identity at launch, which
would make an agent's commits indistinguishable from a person's inside the
sandbox itself.

So: **re-author on landing, not identity at launch.** Record that as the decision
and the reason.

The same step is where the empty-description problem is fixable — a landing that
creates a commit can require a description rather than leaving `(no description
set)` behind.

The vestigial-lineage half of this card overlaps `c72eb6`, which the same design
unblocks. Keep the two separate: this card owns attribution and descriptions,
`c72eb6` owns reaping refs, mirrors and state dirs at acceptance.

Blocked on `c1a6e1` because the seam does not exist until the landing contract
changes.

### Host verification — two findings the implementor did not surface

**1. `jj duplicate` preserves the guest author, and I had not been re-authoring.**
All three commits landed in this series were attributed to
`agent@katsuobushi.local`. The procedure existed in prose and the very next
person to follow it did not. That is evidence about docs-only fixes, not just an
anecdote.

**2. The documented jj command does not exist.** `SKILL.md` gives
`jj describe --author`. There is no such flag in jj 0.41 — `jj describe --help`
has no author option at all. The real command is
**`jj metaedit --update-author`**. Confirmed working. This is the same class of
defect as the `git cherry-pick <name>@sandbox-guest` bug in `c1a6e1`: a
documented command nobody ran.

**3. A cross-card interaction that makes the procedure unfollowable if delayed.**
`c1a6e1` moved guest refs to `refs/remotes/sandbox-guest/`, which jj counts as
**untracked remote bookmarks** — and those are immutable under the builtin
`immutable_heads()`. Because `sandbox dispatch` seeds a guest from the host's
working tree, a later dispatch makes the guest commit a **descendant of the
host's own recent commits**, which therefore become immutable too.

Observed directly: after dispatching `9344ec`, re-authoring the two `c1a6e1`
duplicates failed with `Commit 4ee20cfa is immutable`, while the fresh leaf
re-authored fine. Trace: `immutable_heads() & descendants(qonrtznl)` returns the
`9344ec` guest commit.

**So re-authoring must happen at landing, before any subsequent dispatch.** After
that, the window closes. The procedure as written does not say this, and without
it the requirement is silently unachievable.

**On the central question — is docs-only enough for outcome-shaped criteria?**
The reviewer's answer, which I think is the right shape: *conditionally not
sufficient*. Prose-as-procedure is defensible in principle, because the actor is
an orchestrator that follows this skill and there is no other lever. But two
factual errors make the current prose **unfollowable**, and that collapses the
"prose is the mechanism" argument. Fix those first; revisit the philosophical
question afterwards.

**Confirmed and already handled:** `cherry-pick` alone preserves agent
authorship (verified in a scratch repo — `Author: Agent <agent@katsuobushi.local>`),
and the new prose correctly requires an explicit
`git commit --amend --reset-author --no-edit` after each one.

**BLOCKING A — the jj command does not exist.** `jj describe --author` is not a
flag in jj 0.41. The `-r` part is fine; only `--author` is wrong. An orchestrator
on a jj repo hits an error at this step.

**BLOCKING B — the ordering gap is real and unaddressed.** The prose says the
requirements apply "before the work advances", which a reader will reasonably
take to mean "before merging". That is too late. Once a subsequent dispatch makes
the landed commits ancestors of a new remote bookmark, jj's immutability guard
freezes them and re-authoring fails. The constraint is specifically **before the
next dispatch**, and the prose never says so.

**Verified correct, no change needed:** the stash-cleanup mechanics. The reviewer
tested it — `git stash create` writes no `refs/stash`, the stash SHA is reachable
only through `refs/remotes/sandbox-guest/<name>`, and after deleting that ref plus
`git gc --prune=now` the object is genuinely gone. The gc is required and is
stated.

**Endorsed:** the attribution decision itself. Re-authoring at the duplication
seam keeps the guest branch honest about who ran the command while everything
entering the owner's history carries the owner's identity.

Minor, not blocking: some passive voice against the Simplified Technical English
house style; 46 lines judged proportionate.
