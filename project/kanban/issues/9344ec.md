## What to build

Reading `jj log` after a swarm session shows three kinds of debris. Each is
individually small and together they make the history hard to read and hard to
trust.

- **Commits are not attributed to the owner.** Every commit a sandbox produces is
  authored `agent@katsuobushi.local`. The work is the owner's, landed in the
  owner's repository, and should be attributed to them. Signing may not be
  available in the guest, and that is acceptable — attribution is the requirement
  here, not a signature.
- **Commits with no description survive.** The landing procedure leaves
  working-copy commits with `(no description set)`. In a long session there were
  many. A commit with no message is not reviewable and not bisectable.
- **Vestigial lineages remain after the work is done.** Two sources. `sandbox
  dispatch` seeds a guest from `git stash create`, so each dispatch leaves
  `WIP on (no branch): …` and `index on (no branch): …` commits behind in the
  host repo. Separately, a bounced card's superseded guest commits stay reachable
  from the `sandbox/<inst>` bookmark after the work has landed and the card has
  been accepted.

The first two are host-side landing hygiene. The third overlaps with the existing
card on pruning sandbox refs and mirrors when work is accepted, and with the
`sandbox fetch` orphaning bug — decide whether to fold them together or keep them
separate once that bug's fix is settled.

Attribution is the one with a real design question behind it. The guest commits as
its own identity today, and the host knows whose repository it is. Settle whether
the guest should be given the owner's identity at launch, or whether the host
should re-author on landing, and say which and why.

## Acceptance criteria

- [ ] A commit produced by a sandbox and landed by the host is attributed to the
      repository owner, not to an agent identity.
- [ ] The chosen mechanism (guest identity at launch vs. host re-author on
      landing) is written down with its reason.
- [ ] Landing a branch leaves no commit with an empty description.
- [ ] A dispatch leaves no `WIP on (no branch)` or `index on (no branch)` commit
      behind in the host repo once its card is accepted.
- [ ] Superseded guest commits from a bounced card are not reachable once the
      card is accepted.
- [ ] The landing procedure in the sandbox skill states these as requirements, so
      an orchestrator follows them by default rather than tidying afterwards.


## Design note (from the `c1a6e1` planning pass)

`c1a6e1` settles a landing contract that answers this card's open question about
attribution. Under it the host stops rebasing guest commits and instead
**duplicates** them onto host history (`jj duplicate` / `git cherry-pick`).

That duplicate step is the seam. The copy is created **by the host**, in the
owner's repository, so the host sets the author there. The guest keeps its own
identity in its own branch — which is honest about who ran the command — while
everything that lands in the owner's history is attributed to the owner. That is
strictly better than handing the guest the owner's identity at launch, which
would make an agent's commits indistinguishable from a person's inside the
sandbox itself.

So: **re-author on landing, not identity at launch.** Record that as the decision
and the reason.

The same step is where the empty-description problem is fixable — a landing that
creates a commit can require a description rather than leaving `(no description
set)` behind.

The vestigial-lineage half of this card overlaps `c72eb6`, which the same design
unblocks. Keep the two separate: this card owns attribution and descriptions,
`c72eb6` owns reaping refs, mirrors and state dirs at acceptance.

Blocked on `c1a6e1` because the seam does not exist until the landing contract
changes.
