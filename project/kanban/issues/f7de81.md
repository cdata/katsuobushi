## What to build

Two paths carry the work state off the guest, and both must work.

- **To an attached drive.** The guest reports each work-state transition to the
  host as it happens, so an attached drive narrates a long build instead of
  going quiet.
- **Out of band.** The guest persists the state to the record that
  `sandbox status` reads. An operator with no attached drive still gets the
  answer. This is the property the existing `turn-state.json` design already
  holds, extended to the work state.

The persisted record carries what the status must render: the work state, the
late flag, the label and beating duration of the heartbeat that carries the
state, the newest voluntary report and its time, and the nudge count.

## Acceptance criteria

- [ ] Each work-state transition reaches an attached drive as it happens.
- [ ] The persisted record carries the current work state, the late flag, the
      carrying heartbeat's label and duration, the newest voluntary report and
      its time, and the nudge count.
- [ ] `sandbox status` reports the current work state for an instance that no
      drive is attached to.
- [ ] A transition is reported once, not once per heartbeat interval.

## Review notes

### Round 1 — `review-f7de81-02261512` — VERDICT: needs-changes

**BLOCKING — clippy is not clean, contrary to the implementor's claim.** Two
errors, both in `run_work_state_coordinator`, the card's most important new
function:

- `server.rs:1075` — `map_or(false, |t| t.terminal_reported)` should be
  `is_some_and(...)`
- `server.rs:1127` — `map_or(true, |t| t.elapsed() >= …)` should be
  `is_none_or(...)`

The controller crate is clean; the guest crate is not. 455 controller and 85
guest tests do pass.

**Passed:**

- **A transition fires once per state change, not per tick.**
  `WorkState::Active { is_late }` deliberately does *not* carry
  `duration_secs`, so the comparison at `server.rs:1086` is over
  `(variant, is_late)` only. A duration ticking up leaves the state identical —
  the right non-trigger — while the `is_late` promotion fires exactly once at
  the first tick past the timeout. Both behaviours correct.
- **Throttle cannot skip a forced write.** `is_transition || …` short-circuits,
  so a transition always writes; a failed `spawn_blocking` leaves the timestamp
  unchanged and the next tick retries.
- **Host reading degrades correctly.** `read_work_state` (`status.rs:711`)
  returns `None` on any I/O or parse error; missing and corrupt files are
  covered through the `FakeHost` seam. No crash path.
- **Not journaling the transition is right** — the reviewer's judgement, and I
  agree: transitions are transient mechanical observations, not the agent's
  voice, and journaling them would bury real entries in `reports.ndjson` under
  dozens of `active`/`idle` lines per build. `work-state.json` is the durable
  answer.

**Findings, non-blocking:**

1. **Unstable carrying label.** The primary is picked with
   `max_by_key(duration_secs)` over a `HashMap` iterator (`server.rs:1093`).
   Iteration order is not deterministic, so two heartbeats with equal duration
   can flip the chosen label between ticks. It cannot re-fire a transition (the
   label is not part of `WorkState`) but makes the rendered label and
   `carrying_label` oscillate.
2. **Stale per-label statuses.** The coordinator's
   `HashMap<String, BeatStatus>` never evicts. If a heartbeat task ever died
   while its last status was `beating: true`, that entry would hold the combined
   state at `Active` forever — the precise false-busy this design exists to
   prevent. The loops are too simple to crash in practice, but nothing bounds
   staleness and no test covers it. Filed separately.
3. **The record is written fully but read partially.** All seven fields reach
   `work-state.json`, but `WorkStateRecord` (`status.rs:698`) deserializes only
   four — `nudge_count`, `last_report_text` and `last_report_at` are silently
   dropped by serde. This card's own AC is satisfied; rendering those three is
   `5e545d`'s job, and a note has been added there.
