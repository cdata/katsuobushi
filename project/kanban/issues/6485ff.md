## What happened

The launch recipe snapshots the host Nix database with a plain sqlite CLI
backup, serially, before QEMU starts, with no time bound
(`rust/katsuobushi-controller/src/sandbox/start.rs:638-659`):

```
sqlite3 "$hostdb" '.backup <state>/.nix-db.sqlite.tmp' && mv -f … || true
```

SQLite's backup API restarts from page zero whenever another connection
writes to the source database. The nix-daemon writes `db.sqlite` continuously
while any `nix build` runs (every derivation registration is a write). A
concurrent launch *is* a nix build — so launching sandbox B while sandbox A's
launch (or any unrelated host build) is still building makes the backup
restart indefinitely.

Observed in the field (arcanabasis dispatch, 2026-08): the backup spun for
11m32s at 99.7% CPU with **9.1 TB read and 512 bytes written** — the
signature of the restart loop. The same snapshot standalone (quiescent DB) is
72 MB and completes in under a second; provisioning fell from 11m32s to ~20s
once launches stopped overlapping host builds. The comment at
`lib/sandbox/default.nix:126-127` promises "~0.5s", which is only true on a
quiescent DB. The trailing `|| true` guards *failure*, not *spinning* —
nothing bounds the runtime.

Downstream blast radius: an operator who concludes the step is hung and kills
it leaves no `nix-db.sqlite` in the share (the `&& mv` never runs), the guest
seeding service silently skips on its `ConditionPathExists`
(`lib/sandbox/default.nix:1421`), and the guest boots with a system-only DB —
no dev-shell paths valid, agent unable to run a single gate. (Surfacing that
skip is a separate observability card.)

## Suggested fix

Replace `.backup` with `VACUUM INTO` and add a belt-and-suspenders bound:

- `sqlite3 "$hostdb" "VACUUM INTO '<tmp>'"` takes a consistent read snapshot
  and does **not** restart under concurrent writers — it holds a read
  transaction for the duration instead. Requires sqlite ≥ 3.27 (fine; the
  pinned `pkgs.sqlite` is far newer). `VACUUM INTO` refuses to overwrite, so
  `rm -f <tmp>` first. Keep the `&& mv -f` atomic publish and the `|| true`
  best-effort semantics.
- Wrap the invocation in `timeout` (e.g. 120s) so *any* future pathological
  case degrades to "boot without the seed" — the already-designed fallback —
  instead of wedging provisioning. On timeout, echo a one-line warning into
  the recipe output so the operator knows the guest will boot unseeded.
- Update the `~0.5s` comment at `lib/sandbox/default.nix:126` to describe the
  concurrency behavior.

## Acceptance criteria

- [ ] A launch that overlaps a sustained host `nix build` (something
      continuously registering paths) completes the snapshot step in bounded
      time, and the guest's seeded-DB sanity probe passes.
- [ ] Snapshot failure/timeout is non-fatal, produces no partial
      `nix-db.sqlite` in the share, and prints a visible warning.
- [ ] A unit/integration test (or at minimum the emitted-recipe snapshot
      test) pins the new command shape.
