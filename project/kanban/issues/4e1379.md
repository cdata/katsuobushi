## What happened

The drive watchdog's progress clock is reset **only** by `working`/`info`
reports (`rust/katsuobushi-controller/src/sandbox/prompt.rs:477-484`);
heartbeats are deliberately silent and do not count. The window is a
hard-coded constant — `progressStallSecs = 300`
(`lib/sandbox/default.nix:227`), rendered into the spec but not exposed as a
`lib.sandbox` argument.

A dispatched agent's first act on a fresh VM is typically one long foreground
tool call: a cold workspace compile that consumer projects themselves
document as ~20 minutes (arcanabasis's dispatch instructions say exactly
that). An agent inside one long Bash call emits no reports, so

```
⚠ no progress for 300s — the agent may be stuck (inspect with `sandbox attach`)
```

(`prompt.rs:695-702`) fires on essentially **every** cold launch and is
benign essentially every time. The 2026-08 post-mortem's operator called out
the consequence precisely: the warning trained them toward alarm, and their
one alarmed response was the destructive one (killing a live provisioning
step). A watchdog that always barks is worse than none.

## Suggested fix

Three independent levers; the first two are cheap and worth doing together:

1. **Make the window a consumer knob.** Promote `progressStallSecs` to a
   `lib.sandbox` parameter (like `vcpu`/`mem`) so a project with 20-minute
   cold builds can set 1500s. It already flows spec → watchdog
   (`spec.rs:64`, `progress_stall_secs`), so this is plumbing only.
2. **Neutral first-notice wording.** The first fire in an episode should
   inform, not alarm: e.g. `no reports for 300s — normal during long
   builds; inspect with 'sandbox attach' if unexpected`. Reserve the
   "may be stuck" phrasing for a repeat fire (the one-shot latch in
   `prompt.rs:638`/`:701` would need to re-arm on a longer second window).
3. **(Larger, optional) Count real guest activity as progress.** The guest
   server could observe agent-side signs of life (hook lines, tool-call
   lifecycle from the harness, or even child-process CPU) and bump
   `lastActivityAt`/progress without operator-visible reports. That makes the
   notice mean "genuinely quiet", not "quietly busy". Worth a design pass
   before committing.

## Acceptance criteria

- [ ] A consumer flake can set the stall window per-project; the spec
      snapshot tests cover the non-default value.
- [ ] The first notice's wording no longer asserts the agent may be stuck.
- [ ] Default behavior for existing consumers is otherwise unchanged
      (same window, one-shot semantics preserved).

## Review notes

**Peer review (independent agent), 2026-08-04 — accepted with a test gap closed,
plus one question for the owner.**

AC 1 asked that "the spec snapshot tests cover the non-default value"; every
fixture used the 300 default, so the plumbing could have dropped an override
without failing. Fixed: a spec test now pins a non-default `progressStallSecs`
end-to-end.

**For the owner:** AC 3 says "one-shot semantics preserved", but §2 of this same
card asked for the notice to re-arm on a longer second window — which is what
shipped (two-shot). The card contradicts itself; the implementation follows §2.
Docs that still claimed "one-shot" have been corrected in six places.
