## What happened

An agent's reports exist only as a transient stream: the guest relays each
`report <status> <text>` to the host as a `GuestMessage::Report`, and the
driving `prompt`/`dispatch` process renders it to its own stdout
(`rust/katsuobushi-controller/src/sandbox/prompt.rs:724-736` via the drive
sink). Nothing writes report text durably on either side:

- host-side persistence is `liveness.json` — heartbeat freshness and the
  turn-id counter only (`rust/katsuobushi-controller/src/sandbox/liveness.rs:40-52`);
- guest-side persistence is `turn-state.json` — phase and timestamps only;
  `TurnState` has no text field (`liveness.rs:176-196`,
  `server.rs write_turn_state`).

So a turn can reach `ended-ok` — the *fact* of a clean terminal report is
durable — while the report's *content* is gone if the driving process's
stdout was lost (terminal closed, tmux pane died, orchestrator killed).
Field case (2026-08 post-mortem): a reviewer's `report done "VERDICT: …"`
reached `ended-ok`, the operator lost the stream, grepped the entire
instance state dir for "VERDICT", found nothing, and had to re-prompt the
reviewer to restate its own verdict.

## Suggested fix

Journal reports as NDJSON in the per-instance state dir, host-side, at the
sink where every streamed report already passes through:

- Append each relayed `Report` (plus the `Stopped`/`ReArmed` lifecycle
  verdicts) to `<stateGlob>/<inst>/reports.ndjson` — one JSON object per
  line with `turnId`, `status`, `text`, and a host timestamp. The drive sink
  in `prompt.rs` is the single choke point; `--json` mode already serializes
  `Report` on the wire format, so the record shape exists.
- Best-effort semantics matching the rest of the state dir: a failed append
  warns and never breaks the drive.
- Render the latest terminal report's text in `sandbox status <inst>` detail
  (alongside the existing `turn N ended-ok …` liveness line), so "what did
  it conclude?" is answerable out-of-band without scrollback.
- Optionally mirror guest-side (a sibling of `turn-state.json` on the share)
  for the case where the host process died mid-relay; host-side journaling
  alone already covers the observed failure.

Growth is a non-issue: reports are rare (a handful per turn) and instance
state dirs are already per-instance and reaped with `--remove`.

## Acceptance criteria

- [ ] Killing the driving process's terminal mid-turn, then letting the
      agent finish unattended, leaves the terminal report's full text
      recoverable from `reports.ndjson` and visible in
      `sandbox status <inst>`.
- [ ] `--json` consumers see no change on the stream; the journal is
      additive.
- [ ] A drive test asserts the journal append happens for report,
      stopped, and re-armed events.

## Review notes

**Peer review (independent agent), 2026-08-04 — accepted with a doc correction.**

The card's AC 1 as literally written ("killing the driving process's terminal …
then letting the agent finish unattended") overstates what shipped: the journal
is written by the live drive, so it survives losing that drive's *output* but
not the drive *process*. Guest-side mirroring was explicitly optional in this
card, so the implementation follows the card's own guidance — but the CHANGELOG
and skill docs repeated the overstatement and have been corrected to say what is
actually covered.

The share the journal lives in is guest-writable, so a guest can forge a
verdict; filed as its own card.
