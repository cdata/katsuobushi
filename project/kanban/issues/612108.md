## What to build

The runner from card `51d5d7` loads the heartbeat set exactly once, when the
guest starts, and prints each parse error once at that moment. That satisfies the
design's rule that a broken heartbeat reaches the host once rather than once per
interval — the peer reviewer confirmed the letter of the contract is met and
judged the boundary acceptable for that card.

The consequence is the part worth deciding on purpose. A heartbeat file that is
added, edited or **fixed** after the guest starts is invisible until the guest
restarts. An author who corrects a typo in a `check` body sees no change and has
no signal explaining why.

Settle which reading of "once" the design intends:

- **once ever** — the current behaviour. Then the gap is a documentation problem:
  say plainly that the set is read at startup, and that a change needs a restart.
- **once per error state** — report a broken file once, stay silent while it stays
  broken, and re-evaluate when it changes. Then the runner needs to notice a
  changed directory without reintroducing per-interval error spam.

Prefer the second reading only if it can be done without a watcher that
complicates the runner. Re-reading on a slow timer, or on an explicit signal, may
be enough.

## Acceptance criteria

- [ ] The chosen reading is stated in the design notes, not only in code.
- [ ] If re-reading is implemented: a heartbeat file corrected after startup
      begins beating without a guest restart.
- [ ] A file that stays broken still produces exactly one error, not one per
      interval and not one per re-read.
- [ ] A newly added heartbeat file is picked up under the same rule as a
      corrected one.
- [ ] The behaviour is unit-tested in the pure core, without timers.

## Review notes

### Round 1 — `review-612108-4f889f07` — VERDICT: needs-changes

Gates observed by the reviewer: 565 tests pass, clippy clean, markdown lint
clean. (The commit message claimed 110 tests — that is one binary's count; 565
is the workspace total.)

**BLOCKING — a deleted heartbeat file leaks its task forever**
(`runner.rs:93-96`, `heartbeat.rs:207`). `state.loaded` only ever grows; paths
are never removed, `run_one` is an unconditional infinite loop, and the
`JoinHandle` from `tokio::spawn` is dropped immediately, so no cancellation path
exists. Deleting a heartbeat file leaves its old check body running until the
guest restarts — a removed heartbeat is unremovable. This is the mirror image of
the bug this card was written to fix, and the rescan loop is what makes it
newly surprising: the design now promises to notice file changes, but only ever
in the additive direction.

**Findings, non-blocking:**

1. **The state key is the path, not the path plus the error**
   (`heartbeat.rs:245-249`). A broken file edited into a *different* broken
   state is suppressed, because the path is already in `state.broken`. So the
   implemented rule is "once per broken **path**", not "once per error state" as
   the card, the code and the PDD all now claim. The name overstates the
   granularity.
2. **A working file's content changes are silently ignored**
   (`heartbeat.rs:238`). Once a path is in `state.loaded` it is never re-read,
   so editing a valid check body leaves the old task running the old command.
   Structurally the same gap as the deletion bug.
3. **PDD cross-reference.** The added section (PDD003 lines 190-206) accurately
   describes the code and reads in the document's voice. But the pre-existing
   bullet at line 183 still says "the guest reports the error to the host once"
   with no qualification, so a reader of that line alone still meets the
   ambiguous "once".

**Confirmed working:** a persistently broken file does **not** re-report on each
rescan (`heartbeat.rs:246`, pinned by `it_reports_a_broken_file_exactly_once`);
no double-spawn (`it_does_not_respawn_an_already_running_heartbeat`); the 60s
interval's first tick fires at t=0, so initial load is not delayed; and adding
`source: PathBuf` is a clean change that leaves the parser tests passing.
