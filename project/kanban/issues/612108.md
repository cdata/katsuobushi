## What to build

The runner from card `51d5d7` loads the heartbeat set exactly once, when the
guest starts, and prints each parse error once at that moment. That satisfies the
design's rule that a broken heartbeat reaches the host once rather than once per
interval — the peer reviewer confirmed the letter of the contract is met and
judged the boundary acceptable for that card.

The consequence is the part worth deciding on purpose. A heartbeat file that is
added, edited or **fixed** after the guest starts is invisible until the guest
restarts. An author who corrects a typo in a `check` body sees no change and has
no signal explaining why.

Settle which reading of "once" the design intends:

- **once ever** — the current behaviour. Then the gap is a documentation problem:
  say plainly that the set is read at startup, and that a change needs a restart.
- **once per error state** — report a broken file once, stay silent while it stays
  broken, and re-evaluate when it changes. Then the runner needs to notice a
  changed directory without reintroducing per-interval error spam.

Prefer the second reading only if it can be done without a watcher that
complicates the runner. Re-reading on a slow timer, or on an explicit signal, may
be enough.

## Acceptance criteria

- [ ] The chosen reading is stated in the design notes, not only in code.
- [ ] If re-reading is implemented: a heartbeat file corrected after startup
      begins beating without a guest restart.
- [ ] A file that stays broken still produces exactly one error, not one per
      interval and not one per re-read.
- [ ] A newly added heartbeat file is picked up under the same rule as a
      corrected one.
- [ ] The behaviour is unit-tested in the pure core, without timers.
