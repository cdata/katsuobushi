## What happened

The guest turn machine distinguishes three delivery stages — turn created,
`injected` (the rmcp channel notification was written to the harness's MCP
transport), and `accepted` (the harness actually began the turn, evidenced by
a hook or first report) — see
`rust/katsuobushi-sandbox-guest/src/bin/server.rs:123-139`.

The gap: once `injected` is true, every host resend of that turn id is
dedupe-dropped (`server.rs:236-246`, and the "dropping resend for in-flight
turn" arm at `server.rs:814-819`). But injection success only means
`peer.send_notification(...)` returned Ok (`server.rs:701-714`) — it says
nothing about the harness *processing* the notification. If Claude Code
accepts the transport write and never starts a turn (observed in the field:
harness wedged mid-turn), the state is `injected && !accepted`, which the
machine records but **no recovery path consumes**:

- the host's delivery-deadline resends (up to `deliveryRetries`) all hit the
  dedupe arm and vanish, then the drive bails with "turn N not accepted
  after K resends" (`rust/katsuobushi-controller/src/sandbox/prompt.rs:703-717`);
- `--until-report` is irrelevant (the turn never reached a turn-end);
- the retry-on-failed-injection seam (`server.rs:127-131`) only covers
  injection *errors*, not a swallowed notification.

Field signature (2026-08 arcanabasis post-mortem): `turn-state.json` showing
`turnId: 2, phase: in-flight, acceptedAt: null`, three resends failed, VM
heartbeating normally. Only recovery: `sandbox stop` (pause, keeping the
scratch volume) + restart — a fresh session, so the directive must stand
alone.

## Suggested fix

Two complementary pieces:

1. **Bounded forced re-injection in the guest.** On a resend for a turn that
   is `injected && !accepted && !ended`, after the first dedupe-drop, allow a
   bounded number (1–2) of *re-injections*. The double-run risk is small and
   manageable: a turn that never produced a hook or report has, from the
   harness's perspective, not begun; and the re-injected text can carry a
   guard preamble ("if you already received turn N, continue it; otherwise
   begin it now" — the same self-describing style as the auto-nudge text,
   `server.rs:532-539`). Track a `reinjections` counter on `Turn` so the
   machine stays pure/testable.
2. **An actionable host verdict.** If the turn still never accepts, the drive
   should bail with a *distinct* diagnosis naming the state and the recovery:
   "turn N was delivered to the harness but never began (harness wedged?) —
   restart the session: `sandbox stop <inst>` then `sandbox start --agent
   --name <inst>`, then re-prompt". The current "delivery failed (the agent
   never began the turn)" is accurate but does not distinguish
   transport-level failure (resends might help) from harness-level wedge
   (only a restart helps), and names no next step.

## Acceptance criteria

- [ ] A state-machine test drives `Prompt → Injected → (no activity) →
      resend` and observes a bounded re-injection, then the distinct
      exhausted verdict.
- [ ] The re-injection text carries the already-received guard preamble.
- [ ] The host's exhausted error names the injected-but-never-begun state
      and the stop/start recovery.
- [ ] Normal-path dedupe (accepted or ended turns) is unchanged — a resend
      of an executed turn is still never re-injected.
