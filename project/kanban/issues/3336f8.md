## What to fix

`sandbox dispatch` is documented to stay armed: "An agent that ends its turn
without reporting does _not_ end the drive: the command keeps waiting for a
real `done`/`blocked`." The orchestrator is told to read "the dispatch
returned" as "the work concluded".

That is not what happens. Observed three times in one session driving the
PDD038 thread in `cdata/arcanabasis`:

| card | drive returned | terminal report landed |
| ------ | -------------------------- | ----------------------------- |
| 580353 | on a `working` line | ~14 min later, via auto-nudge |
| 457e37 | on a `working` line | later, via auto-nudge |
| 457e37 | on the bounce turn | later, via auto-nudge |

In each case the last line the drive emitted was a `working` report — for
`580353` it literally read "will follow with a capture-based visual check of
the retuned hit text **before committing**" — and the command exited 0. An
orchestrator that trusted the documented contract would have advanced a card
whose work was not yet committed.

## The worse half: the report is then unjournaled

The skill says a lost terminal does not lose the verdict, because every relayed
report is appended to `reports.ndjson`. It also notes the limit: the journal is
written by the live drive.

Those two facts combine badly here. Because the drive exits **before** the
terminal report, the terminal report is exactly the one that never reaches
`reports.ndjson`. For `580353` the journal's last line was a `working` entry;
the real `done` — which named the commit SHA — was only in `work-state.json`
under `lastReportText`.

So the recovery the skill points at (`sandbox status <name>`, `last report:`)
shows a truncated first line, and the documented journal does not hold the
conclusion at all. The orchestrator has to know to read `work-state.json`,
which no skill mentions.

## What to fix

- Make the armed drive actually wait for a terminal status, or correct the
  skill to say it may return early and name `work-state.json` as where the
  conclusion lives.
- Keep journaling terminal reports that arrive after the drive exits, or say
  plainly in the skill that they are not journaled and where to read them
  instead.
- Either way, an orchestrator must not be told to read a returned drive as
  concluded work while that is false.

## Acceptance criteria

- [ ] A dispatch drive either waits for `done`/`blocked`, or documents that it does not
- [ ] A terminal report that lands after the drive exits is journaled, or the skill names where to read it
- [ ] `sandbox status <name>` surfaces the full terminal report text, not a truncated first line
- [ ] The `sandbox` and `project-orchestration` skills agree with the observed behaviour
