## What to build

F1b of `design/warm-artifacts.md`. The default `sourceInclude`
(`lib/rust/default.nix:40-46`) contains `.cargo`, so flags align out of the box.
A project that overrides `sourceInclude` for its own reasons easily drops
`.cargo` without noticing, which silently decouples every Nix-built artifact
from the dev shell's linker/flag configuration.

`lib.rust` emits a build-time warning when `sourceInclude` omits `.cargo` while
`workspaceRoot/.cargo/config.toml` exists.

Natural home for a broader "is this file really a compile input?" lint later —
a project putting a live tuning file in the Rust source filter forces a full
rebuild on every knob edit — but that is out of scope here.

## Acceptance criteria

- [x] Warning fires on override-without-`.cargo` when a cargo config exists
- [x] Silent when `.cargo` is included, or when no cargo config exists
- [x] Warning names the consequence (artifacts will not match the dev shell)

## Dispatch log

**2026-08-05, host-side.** Implemented in `lib/rust/default.nix` as a
`pkgs.lib.warnIf` wrapping `rustSource`, with a conservative `cargoDirIncluded`
predicate (an entry counts as covering when it is `.cargo`, nested under it, a
whole-tree include, or a filter spec we don't recognise — so it can only
under-warn, never cry wolf).

Verified by temporarily pointing this repo's own `rustLib` call at a
`sourceInclude` without `.cargo` and adding a `.cargo/config.toml`; all
scaffolding reverted afterwards (`flake.nix` restored from backup, `.cargo/`
removed, `nix eval` re-run clean).

- config present + `.cargo` filtered out → warning fires, once per eval
- config present + `.cargo` included → silent
- no config (this repo's real state) → silent

Learned while testing: under flakes `workspaceRoot` is the store copy of the
**tracked** tree, so an untracked `.cargo/config.toml` is invisible to
`builtins.pathExists` — which is correct, since it is equally invisible to the
build it would have affected. Noted in the code comment.

## Review notes

**Peer review 2026-08-05 — NEEDS CHANGES (non-blocking, one-line fix).**

1. `lib/rust/default.nix:84-85` — the comment "an exotic filter spec we don't
   recognise is treated as covering, so this can only under-warn" was **false**.
   `sourceInclude = [ "./.cargo" … ]` and an absolute-string form are both legal
   nix-filter inputs (`_toCleanPath`), both put `.cargo/config.toml` into the
   filtered source, and both tripped the warning — a false positive violating
   this card's own "silent when `.cargo` is included" criterion, whose printed
   remedy ("add \".cargo\"") is confusing to someone who already has it spelled
   differently.
2. `lib/rust/default.nix:87-88` — the `entry.path or null` attrset branch was
   dead code; nix-filter's `include` accepts only function | path | string
   (`_toMatcher`), and an attrset throws inside nix-filter itself.

Cleared: the suspected evaluation throw is **not** present. `x.path or null`
safely returns the default for paths and functions, and `path == null`
short-circuits before `hasPrefix`, so a matcher function never reaches string
coercion. Verified over 13 `sourceInclude` shapes against a scratch fixture.

## Dispatch log — round 2 (review fixes)

**2026-08-05.** The predicate now normalizes each entry instead of matching
literals: `toString` for strings and paths alike, a leading `./` stripped, and a
match on `.cargo`, `.cargo/…`, `…/.cargo` or `…/.cargo/…`. Matcher functions (and
anything else unreadable) still count as covering, but that is now enforced by an
explicit `isString || isPath` guard rather than implied. The false comment at
:84-85 is gone; the dead attrset branch is gone with it.

Re-tested over 7 `sourceInclude` shapes against a scratch fixture holding a real
`.cargo/config.toml` (`scratchpad/lint-cases.nix`), forcing evaluation through
`cargoChecks.rustfmt.drvPath`:

| entry                          | warns | correct |
| ------------------------------ | ----- | ------- |
| `"./.cargo"`                   | no    | ✅ (was a false positive) |
| absolute string to `.cargo`    | no    | ✅ (was a false positive) |
| path value `(root + "/.cargo")`| no    | ✅ |
| `".cargo"`                     | no    | ✅ |
| `".cargo/config.toml"`         | no    | ✅ |
| `"rust"` only                  | yes   | ✅ true positive |
| `nix-filter.lib.matchExt "toml"` | no  | ✅ unreadable ⇒ covering |

## Dispatch log — round 3 (review fixes)

**2026-08-05.** Round 2 found that my fix over-corrected: matching `.cargo`
unanchored (`hasSuffix "/.cargo"`, `.*/\.cargo/.*`) silenced the lint for any
*other* cargo dir, producing four false negatives. The condition the warning is
about is specifically `workspaceRoot/.cargo/config.toml`, so the match is now
anchored there — relative spellings must start at the root, absolute ones must
equal or descend from `toString (workspaceRoot + "/.cargo")`.

Re-tested 12 shapes, and this time each verdict is checked against ground truth
rather than against itself: for every case the harness also evaluates
`builtins.pathExists "${src}/.cargo/config.toml"` on the filtered source, and
asserts the warning fired **iff** the root config is genuinely missing.

**12/12 correct, 0 incorrect verdicts.** The four round-2 false negatives
(`rust/demo/.cargo`, `vendor/.cargo/config.toml`, a foreign absolute
`/nowhere/at/all/.cargo`, and the nested path value) now all warn, while the four
root spellings (`./.cargo`, absolute-at-root, path value, `.cargo/`) stay silent
and the lookalikes (`.cargo-extra`, `rust/.cargofoo`) warn correctly. The matcher
function remains the one deliberate under-warn.
