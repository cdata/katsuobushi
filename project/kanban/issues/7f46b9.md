## What to build

Replace the duplicate-then-repair landing procedure in the `sandbox` skill's
"Change integration" section with a single create.

Today the host copies each guest commit onto its own history (`jj duplicate` /
`git cherry-pick`) and then repairs the copy — `git commit --amend
--reset-author` or `jj metaedit --update-author` for attribution, and a
description fix for an empty message. Every repair is a rewrite, and a rewrite
of a published commit can silently do nothing (card `6d77aa`).

The replacement applies the whole branch as one commit:

```sh
git merge --squash sandbox-guest/<instance>
git commit -m "<type>(<scope>): <card title>"
```

Measured in a scratch repo: this produces a commit authored by the owner, with
every file the branch changed, and it signs under the repository's existing
`commit.gpgsign` configuration. A new commit has no author to inherit, so **no
author flag is needed and nothing is repaired afterwards**.

The name to merge is `sandbox-guest/<instance>` — `sandbox fetch` writes
`refs/remotes/sandbox-guest/<inst>` and that is git's disambiguation form for
it. PDD004 writes `sandbox/<instance>`; the ref namespace from card `c1a6e1` is
the one in the tree.

The message comes from the **card**, not from a commit on the branch. A branch
that bounced twice carries messages like "address review findings", which mean
nothing in the owner's history. The Conventional-Commit prefix comes from the
card `type` (`feature → feat`, `bug → fix`, `chore → chore`, `docs → docs`).

CAUTION to carry into the prose: **do not** land with `git cherry-pick
<branch-tip>`. That applies the tip commit alone, so on a bounced card it lands
the review fix and drops the original work. This is the defect that cancelled
card `186265`.

What goes out of the skill with this change:

- The attribution paragraph and its `--reset-author` / `jj metaedit
  --update-author` instructions.
- The "satisfy both before the next sandbox dispatch" deadline. It exists only
  because a rewrite becomes impossible once a guest ref pins the commit; a
  commit born correct has nothing to race.
- The non-empty-description check. The message now comes from the card.

The guest branch is untouched by the landing, so it stays the review artifact
and the revert artifact.

## Acceptance criteria

- [ ] The skill's landing procedure lands a branch in one create, with no
      metadata rewrite and no immutability override
- [ ] A landed commit carries the owner's name and a valid signature —
      `git verify-commit` reports a good signature. Verified, not asserted
- [ ] The branch tip's author is unchanged by the landing: the guest commits
      still carry `agent@katsuobushi.local`
- [ ] A branch with three commits lands as exactly one commit, whose prefix
      matches the card `type`, and no review-round commit reaches the owner's
      history
- [ ] A two-commit branch lands **both** changes in one commit — verified on a
      real bounce shape, not only on a single-commit branch
- [ ] The operation log for a landing holds one create and no rewrite
- [ ] The skill states plainly that `git cherry-pick <branch-tip>` is wrong for
      a branch, and why
- [ ] The interaction with jj's working-copy commit and `@` placement is tested
      and documented — the landing is a git-side operation in a colocated repo

## Review notes

Peer review by `review-7f46b9-1d85ee8b` (independent VM): **VERDICT
needs-changes, would block on three grounds**. Gates green in-VM (`rust test`
617 passed, `rust lint` clean, `markdown lint` clean) — the blocks are
correctness of the documented procedure, not the gates.

**1. The bounce recipe is unsafe in the normal case (blocking).** Reproduced in
a scratch repo: with `git diff HEAD..sandbox-guest/<name> | git apply --index`,
after an unrelated card lands on `HEAD` between the guest's seed and the bounce,
the diff contains `-unrelated.txt` and `git apply --index` silently stages that
deletion. `git diff A..B` is a two-tree diff, not a range. PDD004's "Drift
between review and integration" says a card landing in between is expected, so
this is the documented normal case, not an edge case. Silent data loss.

**2. The bounce path contradicts the design it implements (blocking).** It
creates `<card title> — review round <n>` commits, so a card that bounces twice
adds three commits. PDD004 requires "One card contributes one commit" and "a
card that bounces twice and then passes adds one commit". It also pre-empts
`08a980`, the card that moves the landing trigger to `ready` — under which a
bounce produces no landing commit at all. The reviewer's recommendation is to
remove the bounce section entirely.

**3. The jj colocated claim is empirically false (blocking).** Reproduced with a
NON-EMPTY working-copy commit: `git merge --squash` does not reset the index, so
pre-existing staged content from jj's `@` stays staged and `git commit` sweeps it
into the landing commit. Confirmed via `git show --name-only HEAD`. The old `@`
was also left orphaned. The author's test used a clean `@`, which is not the case
the acceptance criteria call for.

**4. Commit-type violation (non-blocking, real).** Commit is `feat(sandbox): …`;
the card type is `docs`, and the three Rust files change only doc-comments and
test names — zero behaviour change. Correct prefix is `docs`.

Judged NOT problems: the `dispatch.rs` guard wording is load-bearing for this
change, not scope creep into `c8673c`; and all three deleted sections
(attribution repair, empty-description check, pre-dispatch deadline) are safe to
drop under a squash landing.

Orchestrator's corroborating datapoint: landing `69d1df` in this same session hit
finding 3 for real. `git HEAD` sat at `@-` with the board edits staged in `@`, so
the documented recipe would have swept them into the code commit. Landing
succeeded with `jj new` + `jj restore` of the branch paths, verified
byte-identical to the branch tip.

## Review notes — round 2

Same reviewer (`review-7f46b9-1d85ee8b`), revision delivered into its mirror with
`sandbox deliver`. **VERDICT needs-changes**, one blocker. Gates green
(`rust test`, `rust lint`, `markdown lint`).

Round-1 findings 1 and 2 are **fixed** — the bounce section and its
commit-per-round path are gone, with no dangling cross-references left behind.
Finding 3 is only **partly** fixed: the old index-contamination bug is gone, but
the replacement recipe introduced a new data-loss bug of the same class.

**BLOCKING — unfiltered `jj restore` deletes drifted host work.** Reproduced:
base → guest branch adds `guest-feature.txt` → host drifts, landing
`unrelated-host.txt`. Running the documented recipe verbatim,
`jj restore --from <branch>` with no path filter showed `D unrelated-host.txt`
and `A guest-feature.txt`, and the `jj commit` landed a commit that **deleted**
the unrelated host work. The recipe's own verification — "`git diff
sandbox-guest/<name> HEAD` should produce no output" — exited 0, because the
tree *is* byte-identical to the branch tip. The check certifies the deletion
instead of catching it. On a moved tip the trees should NOT be identical.

The reviewer's way out, which it verified: `jj new` already empties `@`, and with
`@` empty the `git merge --squash` path does a proper three-way merge from the
merge base and preserves drifted host content. So the git recipe is correct once
the WIP problem is solved by `jj new` — the `jj restore` step is both unnecessary
and unsafe.

Judged NOT blocking: the two deletions from the bounce section (the
"never `jj rebase` the bookmark" warning and the `c72eb6` cross-reference) belong
with card `08a980` when it takes over bounce handling.

## Review notes — round 3

Same reviewer, revision delivered with `sandbox deliver`. **VERDICT
needs-changes — one blocking item.** All four gates pass on `5bdb9da`.

Fixed and confirmed: the drift bug is dead. `git merge --squash` on a drifted tip
staged only the branch file and preserved the unrelated host file; both are in
the landing commit, and the scoped diff exits clean on that correct landing.

The scoped diff was also proven able to FAIL, which is what round 2's check could
not do: given a deliberately bad landing (stale file, missing file) it reports
both, and it correctly catches a deletion the landing did not honour.

**BLOCKING — the scoped diff silently passes on paths with spaces.** The
verification uses an unquoted `$(git diff --name-only …)` expansion, which
word-splits on whitespace. Reproduced: a path like `sub dir/file with spaces.txt`
splits into three non-existent arguments, `git diff` finds nothing and exits 0 —
a **false clean on a provably bad landing**. This is not hypothetical for this
repo: `project/design/` holds four space-containing paths today (`PDD001`
through `PDD004`), and any of them can appear on a future landing branch. The
unquoted split silently disarms the only verification step in the procedure.
Fix with bash array quoting (`mapfile -t` + `"${FILES[@]}"`) or `xargs`.

Non-blocking notes: `git diff` exits 0 whether or not it prints, so the "no
output means clean" framing is right for a human but would need `--exit-code` if
automated; and the conditional `jj new` has a narrow gap where a raw `git add`
stages content that `jj status` does not surface clearly — judged an acceptable
simplification. The Conflict reconciliation cross-reference was verified to exist
and be substantive, not a dangling promise.

## Review notes — round 4

Same reviewer. **VERDICT accept.** It reproduced both halves itself rather than
taking the author's word: on a bad landing involving a space-containing path the
old command exited 0 silently while the fixed `mapfile` form printed the diff,
and on a good landing the fixed form exited clean. All four gates green.

Edge cases it examined and judged non-blocking: an empty `FILES` array would turn
the scoped diff into an unscoped whole-tree diff, but a branch that changed zero
files never reaches landing; a filename containing a literal newline would
reintroduce the same class of bug, but `git ls-files` confirms this repo has
none; and `mapfile` is bash-only, which fails loudly rather than silently in a
non-bash shell — strictly better than the false clean it replaced.

Landed at `ready` as one signed, owner-authored commit `4e5b8ea` using the very
recipe this card documents. `git merge --squash` auto-merged `SKILL.md` against
the drifted `deliver` section that had landed meanwhile.

**Observed on landing — a false positive in the accepted verification step.**
The scoped diff reported 28 insertions in `SKILL.md`. The landing was correct;
the difference was exactly the drifted `deliver` documentation, properly
preserved. The check compares the branch tip's version of each touched file
against HEAD, so whenever drift touches the *same file* the branch touched it
reports a difference that is not a defect. Round 4 tested drift in a *different*
file. Filed as a follow-up; the error direction is safe (false alarm, never a
false clean).
