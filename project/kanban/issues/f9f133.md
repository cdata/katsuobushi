## What to build

`rust/katsuobushi-sandbox-guest` gained a YAML parser in card `799ffe`, and the
crate it reached for resolves to literally `serde_yaml 0.9.34+deprecated`.
dtolnay archived and deprecated `serde_yaml` upstream in 2024, so no fix — including
a security fix — will ever land there again.

The immediate risk is low. The parser is read-only, the heartbeat format is
simple, and heartbeat files are version-controlled rather than attacker-supplied.
The peer reviewer on `799ffe` ruled this a follow-up rather than a merge blocker.
It is filed so the deprecation does not simply become invisible once more cards
build on the parser.

Pick the replacement deliberately — do not assume the first fork found. Candidates
worth weighing are `serde_norway`, `serde_yaml_ng`, and `serde_yml`; they differ in
provenance, maintenance activity, and how faithfully they preserve `serde_yaml`'s
behaviour. Block scalars must keep round-tripping byte-for-byte, since heartbeat
`check` and `detail` bodies are shell source.

## Acceptance criteria

- [ ] `serde_yaml` no longer appears in `Cargo.lock` or in any crate manifest.
- [ ] The chosen replacement is named in the commit body with a one-line reason
      covering its maintenance status.
- [ ] Every existing heartbeat parser test still passes, unchanged.
- [ ] A block scalar carrying `'rustc|cargo'` and a trailing newline still parses
      byte-for-byte identically to the `serde_yaml` result.
- [ ] `clippy -D warnings` is clean.

## Review notes

### Round 1 — `review-f9f133-d65885b8` — VERDICT: accept

All acceptance criteria verified empirically by the reviewer, which re-ran the
gates itself: 51 tests pass, `clippy -D warnings` clean, `serde_yaml` absent
from `Cargo.lock` and every manifest. `git show` confirmed only two lines of
`heartbeat.rs` changed (the `from_str` call site) and that the test module was
not touched — the suite was not weakened to accommodate the new crate.

**On the replacement choice — reviewer agreed with the pick**, on evidence
rather than the implementor's rationale:

- `serde_yaml_ng` 0.9.36 is maintained by Antoine Catton, forked from the last
  commit of `serde_yaml` (SHA 2009506d). Both repos link the same commit, so the
  provenance is publicly verifiable.
- It depends on `unsafe-libyaml` 0.2.11 — **identical version and identical
  checksum** (`673aac59…`) to the one the archived `serde_yaml` used. The
  underlying YAML parser is byte-for-byte the same binary, which is what makes
  the block-scalar equivalence argument sound rather than hopeful.
- No new transitive dependencies: `indexmap` 2, `itoa` 1, `ryu` 1, `serde` 1,
  as before.
- The crate's own `test_serde.rs::test_multiline_string` independently verifies
  that `|` preserves trailing newlines and `|-` strips them — precisely the
  semantics the heartbeat `check` and `detail` bodies depend on.

Rejected alternatives: `serde_yml` (community-confirmed provenance concerns —
the `serde_yaml_ng` README calls out its "giant initial commit" anti-pattern,
the same pattern that enabled the XZ Utils backdoor); `serde_norway`
(low adoption).

**Residual risk accepted:** a single-individual maintainer with no
organisational backstop. Still strictly better than an archived crate with zero
probability of any future fix.
